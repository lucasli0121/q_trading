# 分钟成交量口径核对（2026-09-21）

核对 `do_minute_hq_sync_with_time` 中分钟 `volume` / `amount` 的算法是否符合行业口径。

## 一、行业口径

沪深交易所 Level-1 快照里的成交量、成交额、成交笔数都是**当日累计值**，合成分钟的通行做法是先求相邻快照增量，再在窗口内求和。

DolphinDB《基于快照行情的股票和基金 K 线合成》原文：

> 快照行情中的成交量、成交金额和成交笔数都是日累计求和值，所以按照窗口为1分钟、步长为1分钟的滚动窗口计算前，需要先求出两笔相邻快照的增量。

其处理方式是对**完整快照流**（不只窗口内的）做 `deltas`，首条快照的增量为 NULL 时取该快照的累计值本身：

```
iif(deltas(TotalVolumeTrade)==NULL, TotalVolumeTrade, deltas(TotalVolumeTrade)) as DeltasVolume
...
sum(DeltasVolume) as Volume
```

同花顺、信达证券的 tick 切片口径一致：分钟成交量 = 窗口内所有 tick 的成交量之和，其中 tick 成交量是逐笔成交的原始量；若数据源是累计快照，则等价于窗口边界处的累计值相减。

时序边界（同为该文档）：

- 窗口左闭右开，输出时间为窗口左边界；
- 早盘集合竞价归入第一根 K 线，第一根窗口 `[09:25:00, 09:31:00)`，输出 09:30:00；
- 尾盘集合竞价 14:57–15:00 归入 15:00 那根；
- 每交易日 240 根，含 11:30:00 / 14:57:00 / 15:00:00，不含 14:58:00 / 14:59:00。

tickflow 的 `quote.volume` / `amount` 同样是当日累计值：官方文档示例 600000.SH `last_price=9.72, volume=426585, amount=422430500`，`amount / volume ≈ 990 ≈ 9.72 × 100`，即 `volume` 单位为手；且 42.6 万手对应单日量级，3 秒快照不可能有这个数，可确认是累计值。

## 二、当前实现与口径的差异

```python
volume_sum_diff = sum(
    rt_records[i].get("volume", 0) - rt_records[i - 1].get("volume", 0)
    for i in range(1, count)
)
```

这个求和式会望远镜消项，恒等于 `末条.volume - 首条.volume`。也就是说：

- 形式上做了 n-1 次减法，实际只用到首尾两条记录的累计值，中间记录全被抵消；
- **窗口内首条快照的增量被丢掉**。该增量 = 首条累计 − 上一窗口末条累计，是上个窗口结束到本窗口首条快照之间真实成交的量。

窗口取 `[now - minute_sync_interval 分钟, now - 1 分钟:59]`，相邻两轮首尾相接不重叠，所以缺的就是采样间隔那一段的量。

量化结果（成交速率恒定，窗口 120 秒，真实量 12000）：

| 每股采样间隔 | 窗口内条数 n | 当前算法 | 行业口径 | 偏差 |
| --- | --- | --- | --- | --- |
| 6s | 20 | 11400 | 12000 | −5.0% |
| 12s | 10 | 10800 | 12000 | −10.0% |
| 30s | 4 | 9000 | 12000 | −25.0% |
| 60s | 2 | 6000 | 12000 | −50.0% |

即偏差恒为 `-1/n`，n 为窗口内该股票的采样条数。

按当前额度（`max_requests_per_minute=9` × `real_time_stock_limit=5` = 45 标的/分钟）折算每股采样间隔 `s = 4N/3` 秒：

| 单实例股票数 N | 采样间隔 s | 窗口内条数 n | volume 偏差 |
| --- | --- | --- | --- |
| 9 | 12s | 10 | −10% |
| 36 | 48s | 2.5 | −40% |
| 45 | 60s | 2 | −50% |

`amount` 用同一写法，偏差相同。

## 三、修法

正确的窗口量 = 窗口内末条累计 − 窗口开始前的末条累计：

```
volume = last_rec["volume"] - baseline
amount = last_rec["amount"] - baseline_amount
```

`baseline` 取该股票在 `start_time` 之前（当日）的最后一条 rt 记录的累计值；当日无更早记录时 `baseline = 0`，此时结果等于末条累计值本身，与「首条快照增量取累计值」的规则一致，也自然包含了早盘集合竞价的量。

实现上不需要逐条累加，也不必新增查询：把现有查询的 `start_time` 往前放宽（`baseline_lookback_minutes`，默认 30 分钟），取回后按 `create_time` 切两段——`< start_time` 的只留最后一条作 baseline，`>= start_time` 的作为窗口记录。放宽窗口多取的记录量很小（受额度约束，每股每分钟最多约 5 条），并顺带获得两个保护：

- 用 `last - baseline` 替代首尾作差后，窗口内只剩 1 条记录时也能算出正确量（当前写法在 n=1 时结果为 0）；
- 累计值出现回落（跨日、数据源异常）时 `last < baseline`，可判为异常并按 0 处理，避免写入负数。

同时建议删掉那个 n-1 次减法的循环，它不产生任何效果。

## 四、附带确认

`turnover` / `amp` / `qrr` 取窗口内算术平均，`turnover` 严格说是累计换手率的增量而非平均值，`amp` 当日振幅在窗口内基本不变，算术平均与取末条差别很小，本次不动。

## 五、落地结果

已按确认的口径修改 `stock_fetch/stock_fetch.py`。

新增三个模块级纯函数（便于离线验证，不依赖项目依赖）：

| 函数 | 作用 |
| --- | --- |
| `pure_stock_code` | 取 code 的纯数字部分，跨 `000001` / `000001.SZ` / `sh000001` 归组 |
| `session_open_of` | 取交易日开盘时间；交易所日历异常时退回 09:30 |
| `split_minute_window_records` | 按窗口左边界把查询结果切成「窗口内记录」与「窗口前末条基线」，组内按 `create_time` 升序 |
| `cumulative_delta` | 按 `末条累计 − 基线` 算增量，返回是否用到了基线 |

`do_minute_hq_sync_with_time` 的改动：

- 新增 `baseline_lookback_minutes`（默认 30），查询起点前移取基线，并在 `>= 当日开盘` 处夹紧（开盘前的快照累计值只是集合竞价量，不能作连续竞价的基线）；
- `first_window` 判定：窗口起点落在开盘后第一个窗口内时以 0 为基线，因此当日首根分钟线包含集合竞价成交量；
- 基线缺失且非首窗（服务中途启动、数据缺口）时退回首尾作差，并按窗口打一条告警；
- 累计值回落（跨日残留、数据源异常）时按 0 处理并告警，不写入负数；
- 删掉原来的 n-1 次减法循环。

### 验证

本机无项目依赖，用 `ast` 抽出上述函数与方法，配合 stub 的 DAO、日志对象与交易所日历执行，7 组场景：

| 场景 | 结果 |
| --- | --- |
| 常规窗口，采样间隔 60s（n=2） | 改造前 6000 → 改造后 12000，真实 12000 |
| 常规窗口，采样间隔 6s（n=20） | 改造前 11400 → 改造后 12000，真实 12000 |
| 当日首窗 | 查询起点夹到 09:30:00；基线缺失但判定为首窗，成交量 36600（含集合竞价 30000） |
| 窗口内仅 1 条记录 | 改造前恒为 0 → 改造后 6000 |
| 无基线且非首窗 | 退回首尾作差，成交量 0 并告警 |
| 累计值回落 | 由 −1498800 归零并告警 |
| code 格式混存三种 | 归为 1 组，只产出 1 条分钟记录 |
| 交易所日历抛异常 | 退回 09:30，流程不中断 |

语法检查通过，无 `volume_sum_diff` / `range(1, count)` 等旧写法残留。

### 历史数据
