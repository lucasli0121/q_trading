# 修改完成报告：MQTT 池级订阅全程空转（2026-10-10）

## 一、现象

本机调试实例「一直收不到订阅消息」。推送端一侧全部正常：

```
2026-10-10 11:58:52,551-INFO-推送成功 topic=q_share/stock/minute/6aa2c3c6276f35f51fc34e5b/688825.SH
payload={"code": "688825.SH", "name": "长鑫科技", ...}
```

本端 `log/info.log` 里两次启动（10-09 23:18、10-10 11:56）都只出现一条订阅记录：

```
11:56:16,857 workflow.strategy_workflow-392-INFO: 收集到 4 个 pool_id: {'6a6b695628893aa08c08522a', '6abb99fd276f35f51ff9f2d2', '6a58b9e928893aa08c3eb62c', '6aa2c3c6276f35f51fc34e5b'}
11:56:58,959 mq.mqtt_client-419-INFO: MQTT 订阅 topic 成功: q_share/config_change (QoS: 1, mid=1)
11:57:47,007 workflow.strategy_workflow-294-INFO: 已订阅配置变更通知: q_share/config_change
```

`grep -c "已订阅股票池行情" log/info.log` = **0**，而推送的 pool_id `6aa2c3c6276f35f51fc34e5b`
就在那 4 个池里。两点可直接定位：

- `mid=1` 说明 `config_change` 是本次连接发往 broker 的**第一个** SUBSCRIBE 包 —— 池级订阅一个都没发；
- `_subscribe_mqtt()` 返回 True、没有任何 WARNING/ERROR，故障完全静默。

## 二、根因

`_pool_ids` 一个集合承担了两种语义，两种语义在启动路径上互相破坏。

1. `StrategyWorkflow._init_workflow()` 把「**打算订阅**的池」预填进 `self._pool_ids`（4 个）；
2. `BaseWorkflow.subscribe_pool()` 用「**在 `_pool_ids` 里**」判断「**已经订阅**」，命中即短路返回：

```python
with self._pool_lock:
    if pool_id in self._pool_ids:
        return True          # ← 只登记过、从未 subscribe，也被当成订阅成功
    self._pool_ids.add(pool_id)
```

3. 于是启动时的订阅循环整个空转：

```python
if self._pool_ids:                      # 非空（是预填的）
    for pool_id in self.pool_ids:       # 4 个
        self.subscribe_pool(pool_id)    # 全部在第 1 步短路 → broker 侧 0 个订阅
else:
    ... 全局通配 ...
```

登记表记录 4 个池，broker 侧 0 个订阅，二者完全脱节且不报错。

**为什么长期没被发现**：`tests/test_config_reconcile.py` 的 harness 用替身替换了 `subscribe_pool`，
启动订阅路径从未被真实走过；真实 MQTT 端到端只能靠部署验证。

## 三、修法：意图与事实分开

`_pool_ids` 只保留一个含义 —— **已经真正 subscribe 成功的池**。「打算订阅哪些池」由新的基类钩子提供。

### `workflow/base_workflow.py`

- `__init__` 里 `_pool_ids` 的注释写明语义，并明确「启动前不要预填」及其后果；
- 新增钩子：

```python
def _collect_startup_pool_ids(self) -> list[str]:
    """返回启动时需要订阅的股票池 ID，子类可重写。"""
    return []
```

- `_subscribe_mqtt()` 改为按钩子返回值订阅：

```python
startup_pool_ids: list[str] = self._collect_startup_pool_ids()
if startup_pool_ids:
    for pool_id in startup_pool_ids:
        self.subscribe_pool(pool_id)
else:
    ... 全局通配（兼容模式）...
```

### `workflow/strategy_workflow.py`

- `_init_workflow()` **不再写 `_pool_ids`**；
- 池收集逻辑搬到 `_collect_startup_pool_ids()`，去重后 `sorted()` 返回；
  `收集到 N 个 pool_id` / `未收集到任何 pool_id` 两条日志随之外移，仍在启动阶段输出。

对账路径（`subscribe_pool` / `unsubscribe_pool` / `_sync_pool_subscriptions`）语义不变，未受影响：
运行时新绑定的池不在 `_pool_ids` 里，`subscribe_pool` 会正常订阅并登记。

### 探针（替换 `AppContext`，不连 broker）

```

未真正订阅的 pool: ['6a6b695628893aa08c08522a', '6aa2c3c6276f35f51fc34e5b']
```

修复后：

```

 - q_share/stock/real_time/6aa2c3c6276f35f51fc34e5b/#

 - q_share/stock/minute/6a6b695628893aa08c08522a/#

未真正订阅的 pool: []
```

### 新增回归守卫 `tests/test_mqtt_pool_subscription.py`（8 项）

守住三件事：

1. 启动时每个待订阅池都必须真的 subscribe 到 `real_time` 与 `minute` 两个 topic；
2. `_pool_ids`（已订阅登记表）成员**必须都有对应的订阅记录** —— 预填会让这条断言失败；
3. `subscribe_pool` 的幂等只针对「真的订阅过」的池，重复订阅仍只打一次 broker。

另有 `StrategyWorkflow` 侧的 wiring 测试：`_init_workflow()` 后 `_pool_ids` 必须为空、
`_collect_startup_pool_ids()` 必须返回用户策略绑定的池集合、真实 `_subscribe_mqtt()` 必须覆盖到每一个池。

## 五、生效条件（用户侧）

本机实例当前进程（11:56 启动）仍在「只订阅 config_change」的状态，**必须重启**才会带上本修复。
生成机器跑的是打包产物，源码改动不会自动生效，需重新部署/打包。

排查同类问题的一句口诀：日志里出现 `MQTT 订阅 topic 成功: q_share/config_change (mid=1)`
且没有任何 `已订阅股票池行情`，就是池级订阅全程空转。
