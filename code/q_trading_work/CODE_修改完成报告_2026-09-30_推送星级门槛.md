# 推送/下单星级门槛 — 修改完成报告

日期：2026-09-30
范围：`code/q_trading_work`（本端）。服务端已在部署版本中提供 `push_buy_min_star` / `push_sell_min_star`，本端只做读取与过滤。

## 一、需求与确认的口径

需求：读用户偏好里的两个星级门槛，交易通知只通知达到门槛的信号，产生订单也按同一门槛过滤。

落地前确认了三点（含两处会做反的地方）：

| 项 | 结论 |
| --- | --- |
| 比较口径 | 阈值 `<= 0` 表示不限；否则 `star >= 阈值`（含边界，与服务端信号列表 `min_star` 的 `$gte` 一致） |
| 拦截范围 | MQTT 实时信号流 + 企业微信/微信推送**都拦**；信号仍写库 |
| 订单 | 买入按 `push_buy_min_star`、卖出按 `push_sell_min_star` **都拦** |

`star` 由策略侧给出（10 分制打分折算：买入 `score/2`，卖出 `-score/2`），随信号写库，本端不重新计算。

## 二、改动清单

### 1. `trade/notifier.py`（+191 行）

新增门槛解析与判定：

- `parse_min_star(value)`：原始值 → 非负 float。`None` / 空串 / 非数值 / 负数 / `NaN` 一律归到 `0.0`（不限），不抛错也不产生负门槛。
- `star_passed(star, min_star)`：纯函数，阈值 `<= 0` 放行，否则 `star >= 阈值`；`star` 非法时视为不达标（阈值 > 0 而信号没有星级不能当高星放过）。
- `get_push_min_star(user_strategy_id, action)`：按方向取买/卖门槛。方向既不是「买入」也不是「卖出」时返回 0（不限）：策略只会给出这两种 action，落在这里说明上游数据异常，此时拦下单的代价远大于放过。
- `_resolve_user_id` / `_resolve_min_stars`：两级实例缓存，TTL 沿用 300 秒。
- `invalidate_preferences_cache()`：清空偏好、user_id、门槛三份缓存，供对账心跳调用。

`notify_signal` 增加 `min_star` 参数与返回值（`bool`）：未达门槛直接返回 `False` 且不发消息；调用方已解析过门槛时传进来，省掉一次解析。文案拼装逻辑未动。

### 2. `workflow/strategy_workflow.py`

`_save_trade_signal` 里解析一次门槛，三个出口共用同一个布尔值：

- 未达门槛：信号照旧 `POST /api/trade_signal/add`（界面按星级筛历史信号依赖这份记录），但跳过 MQTT 发布、跳过文本推送，并记一条 INFO 说明 star 与门槛；
- 返回值语义仍是「能否继续下单」：未达门槛返回 `False`，`_process_bar` / `_process_tick` 据此直接 `return`，与信号风暴过滤共用同一条退出路径，因此**不需要**在下单分支里再判一次。

`reconcile_user_strategies`（上一轮的 60 秒对账）新增第 8 步：调用 `invalidate_preferences_cache()`。偏好不在对账对象里，但这是「界面改了配置要跟随」的唯一心跳，顺手清缓存把门槛改动生效时间从最长 300 秒（通知器 TTL）压到最长 60 秒。

同时删掉上一轮留下的死字段 `self._reconciling`（只赋值、从未读取，并发保护实际用的是 `_reconcile_lock`）。

### 3. `dao/user_preference.py`

服务端新增的两个字段在本端 DAO 上的对应（含 `from_db` / `to_db`）。本端通知器走的是 `PreferenceApi` 返回的字典，不经过 DAO，这里是口径声明。

### 4. 测试

- 新增 `tests/test_push_star_filter.py`：23 项 + 14 个子用例，覆盖解析边界、`>=` 含边界、三级失败兜底、缓存命中与失效、`notify_signal` 自身拦截、`_save_trade_signal` 三出口、以及 `_process_bar` 端到端（低星信号连持仓都不去拉）。
- `tests/test_config_reconcile.py` 新增 1 项：对账必须清理门槛缓存。
- `tests/test_strategy_workflow.py` 补桩：见下一节。

## 三、关键取舍与踩到的坑

**门槛判定只算一次。** 三个出口各判一次必然分叉（改一处漏一处），所以 `_save_trade_signal` 解析后往下传：MQTT 用它，`notify_signal(min_star=...)` 用它，返回值也用它。

**失败兜底一律是「不限」。** 门槛同时决定下单，读不到偏好时按「不限」等于回到改动前的行为；按「拦全部」兜底，一次接口异常就会让整个实例停止下单。

**user_id 解析失败不写缓存。** 偏好缓存本身 300 秒，如果连 user_id 失败也缓存成空，一次网络抖动会让门槛静默失效一整个 TTL。查不到时本轮按不限处理但下次信号重试。

**门槛必须缓存。** 判定发生在每条信号上（分钟级、逐股），解析门槛要走 user_strategy → user_id → preference 两次 HTTP。实测首轮 1~2 次（同一 user_id 的策略复用偏好缓存时 1 次），之后每个信号 0 次。

**`star=0` 且门槛 > 0 的信号会被拦。** 这是 `>=` 口径的必然结果，也符合「没打星就不能算高星」。当前三个策略的分钟买入与卖出路径都带 `star`（强趋势走基类 `_check_buy_conditions` / `_check_sell_conditions`，波段的卖出分项、成交量放大的 `_to_star`），所以正常链路不会命中；一旦命中会有一条 INFO 打出 star 与门槛，可据日志排查。

**测试桩 `MagicMock` 被 `float()` 读成 1.0。** `tests/test_strategy_workflow.py` 的通知器是裸 `MagicMock`，`get_push_min_star()` 的返回值也是 `MagicMock`，而 `MagicMock` 支持 `__float__`，于是门槛被解析成 1.0，把所有信号都拦掉，表现为 3 个「保存信号」用例莫名返回 `False`。已在桩上显式写 `get_push_min_star.return_value = 0.0` 并注明原因。

## 四、验证

- 新增测试：`tests/test_push_star_filter.py` 23 项全过；`test_notifier.py` + `test_config_reconcile.py` + `test_push_star_filter.py` 合计 76 项全过。
- 全量回归：`594 passed, 2 skipped`（排除两个联网选股用例；命令见下）。
- 只读探针（连生产服务端，无写操作）：5 个用户策略全部解析出 user_id；偏好返回体都含 `push_buy_min_star` / `push_sell_min_star` 两个字段，当前值均为 `0.0`，即**当前行为与改动前完全一致**，不会突然拦掉任何信号。缓存行为实测：首轮 1~2 次 HTTP，同一门槛再取 0 次。
- 判定表实测：门槛 3.0 时 `star=2.5 → 拦`、`star=3.0 → 放行`、`star=3.5 → 放行`；门槛 0.0 时全部放行。

## 五、部署与生效

1. 本端重启一次（或等上一轮的配置热更新流程带起新代码）。
2. 服务端无需再改。
3. 之后在界面改门槛**不需要重启**：对账每 60 秒清一次门槛缓存，下一次推送/下单就会重新读；清缓存本身不发请求，只有真正推送/下单时才拉一次偏好。
4. 预期日志：低于门槛时出现「星级未达门槛，不发 MQTT、不推送、不下单（信号已写库）: action=…, star=…, min_star=…」。

## 六、边界

- **回测链路不涉及**：`backtest/` 下没有任何推送或门槛调用，回测是信号级复现，不进推送与下单链路。
- **成交回执不做星级过滤**：订单已经过门槛，回执是成交事实，拦掉只会让「有持仓却收不到回执」。
- **界面/CLI 未接**：服务端已校验门槛取值 0~5，但小程序与 `q_trading_cli` 的偏好设置页还没把这两个字段暴露成可编辑项（`q_trading_cli/dao/user_preference.py` 两侧字段已就位）。
- **当前配置全为 0**：要让门槛真正起作用，需要在界面上把值改成 0 以外的数（例如 3）。
