# 回测写库缺陷修复报告（2026-09-14）

> 需求：**回测跑完后没有写数据库，改成写数据库。**
> 服务端接口（POST 保存 / GET 查询，均按策略模板 ID 关联）：
> `POST /api/strategy/{strategy_id}/backtest`、`GET /api/strategy/{strategy_id}/backtest`
> 回测对象使用 `dao/backtest_dao.py`；新增 API 接口并完成回测保存。

---

## 一、缺陷定位

排查后发现**不是「没有保存代码」，而是三个环节都没接上**：

| # | 现状 | 问题 |
|---|---|---|
| 1 | `dao/backtest_dao.py` 的 `BacktestDao` **全仓只被定义、从未被引用**（`grep` 仅命中第 19 行的类定义） | 回测结果没有统一的数据载体 |
| 2 | `backtest/backtest_engine.py::save_results()` 直接手搓 dict 塞给 `StrategyApi.save_backtest()` | 字段口径散落在引擎里，无对象约束、无查询侧解析 |
| 3 | `run()` **只有回测逻辑，没有保存动作**；保存只由 `backtest/main.py --save` 触发 | **回测跑完默认不写库**（就是本次要修的缺陷） |

同时 `api/strategy.py` 下虽已有 `save_backtest` / `get_backtest`，但回测语义挂在「策略模板 API」里，职责不清。

负责人现场确认的三项设计口径：

1. **保存时机**：`run(save=True)` **显式开启**（默认不写库，避免调试回测污染 `backtest_tbl`）；
2. **`BacktestDao` 角色**：回测结果的**唯一数据载体**（保存与查询都走它）；
3. **API 位置**：**新建 `api/backtest.py`**（原 `StrategyApi` 两个方法保留为兼容转发）。

## 二、服务端契约（已核对代码，非猜测）

| 项 | 内容 | 出处 |
|---|---|---|
| 保存 | `POST /api/strategy/{strategy_id}/backtest`，请求体 `BacktestSaveRequest` = **只有 `result_data` 一个字段** | `q_trading_server/web_api/models.py:198` |
| 落库 | `backtest_tbl` 只写 **`strategy_id` / `result_data` / `create_time`** 三个字段，`create_time` 由服务端生成 | `db/mongo/mongo_backtest_impl.py:26`、`routers/strategy.py:148` |
| 校验 | 保存/查询前先校验策略存在，不存在返回 404「策略不存在」 | `routers/strategy.py:141-144` |
| 查询 | `GET` 返回 `list`，按 `create_time` **倒序**，`_id` 转字符串 | `mongo_backtest_impl.py:41` |
| 认证 | 两个接口都需要 Bearer token（`get_current_user`） | `routers/strategy.py:137/161` |

> 关键推论：服务端**不单独存**收益率/回撤/频率等标量字段，它们必须打包进 `result_data`。
> 因此 `BacktestDao.to_result_data()` 会把**全部标量字段 + trades + summary** 合并成一份自描述 JSON，
> 前端拿到单条记录即可还原全部指标。

## 三、代码改动

### 3.1 `dao/backtest_dao.py` —— 升级为唯一数据载体（+ 约 200 行）

新增能力：

| 方法 | 作用 |
|---|---|
| `to_result_data()` | 组装写入服务端 `result_data` 的完整 JSON（标量字段 + `trades` + `summary`） |
| `to_payload()` | 组装 HTTP 请求体 `{"result_data": {...}}`（对应服务端 `BacktestSaveRequest`） |
| `to_db()` | 组装服务端 Mongo 文档形态 `{"strategy_id", "result_data", "create_time"}` |
| `from_db(data)` | **兼容两种形态**解析：① 服务端嵌套文档（标量在 `result_data` 内层）② 扁平记录 |
| `from_db_record(data)` | 类方法：服务端记录 → `BacktestDao` |
| `from_summary(...)` | 类方法：`BacktestSummary` + `TradeResult` 列表 → `BacktestDao` |
| `_trade_to_dict()` | 交易明细转可 JSON 序列化字典（同时兼容 dict 与 `TradeResult`） |

**单位口径**：回测汇总里收益率/回撤是**百分数**（`12.5` 表示 12.5%），写入 DAO 时统一换算为**比例**
（`0.125`），与服务端字段注释「如 0.15 表示 15%」保持一致 —— 该换算集中在一处，不再散落引擎里。

### 3.2 `api/backtest.py` —— 新增（新文件，约 110 行）

```python
class BacktestApi:
    def save(self, dao: BacktestDao) -> str                       # POST，body=dao.to_payload()
    def save_result_data(self, strategy_id, result_data) -> str   # 兼容旧调用方
    def get(self, strategy_id) -> list[BacktestDao]               # GET → 解析为 DAO 列表
    def get_raw(self, strategy_id) -> list[dict]                  # GET → 原始记录
```

- `save()` 在 `strategy_id` 为空时抛 `ValueError`（**不发出无效请求**）；
- `get()` 自动跳过非 dict 的脏记录；
- 已在 `api/__init__.py` 的 `from ... import` 与 `__all__` 中导出。

### 3.3 `api/strategy.py` —— 兼容转发

`save_backtest(strategy_id, result_data)` / `get_backtest(strategy_id)` **签名与返回值不变**，
内部改为委托 `BacktestApi`，老调用方与既有测试零改动。

### 3.4 `backtest/backtest_engine.py` —— 接入 DAO + BacktestApi

- `__init__` 新增 `self._backtest_api: BacktestApi`；
- **`run()` 新增 3 个参数**：

```python
def run(self, strategy, save=False, strategy_id="", user_strategy_id="")
```
  回测结束后若 `save=True`，自动调用 `save_results()` 写库（失败仅告警，不打断返回）；
  显式传入的 `strategy_id` 会**回写到策略实例**，优先级高于按名称回填的结果；

- `save_results()` 内部改为 `BacktestDao.from_summary(...)` → `BacktestApi.save(dao)`，
  异常处理（`HTTPStatusError` / 其他）与 `user_strategy_id` 执行指标同步逻辑保持不变。

### 3.5 `backtest/main.py` —— CLI 修正

- 新增 `--user-strategy-id` 参数（保存后可选同步策略执行指标）；
- **修正原有隐性 bug**：原来把**策略类**（而非实例）传给 `save_results()`，
  导致实例上的 `strategy_id` 丢失、`strategy_name` 只能取类属性；
  现在先实例化一次，`run()` 与 `save_results()` 复用同一实例。

### 3.6 文档

`CLAUDE.md` 的 Backtesting 章节补充了 `run(save=...)`、`BacktestDao` → `BacktestApi` →
`POST /api/strategy/{id}/backtest` 的持久化链路与 CLI 用法。

### 7.4 顺带发现并修复的 3 个缺陷

真实链路跑通后，暴露出 3 个**此前 mock 测试覆盖不到**的问题：

#### (1) `_bind_strategy_id` 只按名称查 → 永远回填失败（严重）

**现象**：日志 `按名称查询策略[强势反弹策略] 失败，跳过回填 strategy_id: 404 Not Found`。

**根因**：本端策略类名与后台模板显示名**不一致**（实测）：

| 本端类 | 类内 `strategy_name` | 后台模板名 | 后台 `class_name` |
|---|---|---|---|
| `StrongReboundStrategy` | 强势反弹策略 | **强趋势策略** | `StrongReboundStrategy` |
| `SwingTradingStrategy` | 低频波段交易策略 | **波段交易策略** | `SwingTradingStrategy` |

按名称查 → 两者都 **404** → `strategy.strategy_id` 恒为空 →
`run(save=True)` 不传 `strategy_id` 时**静默跳过写库**；分钟频回测也无法按 id 取当日选股列表。
（CLI 因为强制 `--strategy-id` 才掩盖了这个问题。）

**修复**：`_bind_strategy_id` 改为**名称优先、类名回退**，新增
`_query_template_by_name()` / `_query_template_by_class_name()`；
名称未命中降级为 `debug`（避免刷 404 噪音），最终仍未命中才 warning。
实测修复后自动回填成功（`strategy_id` 由 `''` → `6a5884d5…`）。

**回归用例（+5）**：`tests/test_backtest.py::test_bind_strategy_id_by_name`、
`::test_bind_strategy_id_falls_back_to_class_name`、`::test_bind_strategy_id_keeps_previous_when_unresolved`、
`::test_bind_strategy_id_ambiguous_class_name_takes_first`、`::test_bind_strategy_id_handles_list_error`。

#### (2) 零交易时 `trading_days` 被漏算（显示误判）

**现象**：第二次回测输出「**交易天数: 0**」，而第一次是 73。

**根因**：`_compute_summary()` 在 `if not trades:` 处**提前 return**，跳过了 `trading_days` 赋值
（该字段本与是否有交易无关，纯按回测区间估算）。

**修复**：把 `trading_days` 计算**前移到早退之前**；后续年化收益复用同一变量（去掉重复计算）。
修复后 0 交易回测也正确显示 `trading_days=73`（已实测）。

**回归用例（+1）**：`test_summary_without_trades_still_reports_trading_days`。

#### (3) `_run_daily` 未关闭 Redis（与 `_run_minute` 不对称）

**根因**：`_run_minute` 有 `cache.set_redis_enabled(False)`，`_run_daily` **没有**。
`set_redis_enabled` 的 docstring 明确写着「回测等离线场景应调用 `set_redis_enabled(False)`」。
后果：日频回测会把 `select:` / `score:` 键**写进与实盘共用的 Redis**，污染生产缓存。

**修复**：抽出 `_run_daily_inner()`，外层 `_run_daily()` 与分钟频对称地开关 Redis
（`try/finally` 保证异常时也恢复）。

**回归用例（+2）**：`test_run_daily_disables_redis_cache`、`test_run_daily_restores_redis_on_error`。

### 7.5 ⚠️ 未闭环：同一配置重复回测**结果不可复现**（需你决策）

这是本轮**唯一未解决**的问题，且**不是本次改动引入**（改动前就存在）。

**实测证据**（同一配置 `600519,002415` / `2026-06-01 ~ 2026-09-12` / daily，反复跑）：

| 次序 | 交易笔数 | 收益率 |
|---|---|---|
| 第 1 次 | 2 | +5.43% |
| 第 2 次 | 0 | 0.00% |
| 第 3 次 | 4 | −4.87% |
| 第 4 次 | 3 | −11.13% |
| 第 5 次 | 0 | 0.00% |

**定位过程与结论**：

1. `strategy.select()` 自身是**稳定的**（同参数连调 3 次结果完全一致）。
2. 但 `select` 有时对全部股票返回 `{"matched": false, "extra": {"reason": "no data"}}`
   → 当日候选为空 → 0 笔交易。
3. `reason: "no data"` 来自 `BaseStrategy.load_his_daily_data()`：
   取数窗口 `2026-06-18 ~ 2026-07-28`，**服务端 `/api/market/kline/day` 间歇性
   返回 HTTP 500**（实测：不带日期参数时稳定 500；带日期时正常返回 28 根）。
4. 该异常被 `load_his_daily_data` 的 `except Exception` **吞掉且只记 `debug` 日志**
   → 全程无告警，表现为「交易天数正常但一笔交易都没有」。

⇒ **根因是服务端行情接口不稳定 + 本端静默降级**，不是回测算法或写库链路的问题。

**需要你决定**：

- **A**：先找后台确认 `/api/market/kline/day` 的 500 原因（不带日期参数即 500，疑似必现分支）。
- **B**：本端提高可观测性 —— 把 `load_his_daily_data` 的取数异常从 `debug` 提到 `warning`，
  并在 `select` 结果里区分「取数失败」与「正常不满足条件」，避免静默 0 交易。
- **C**：回测侧加「取数失败重试 N 次 + 失败即中止并报错」，避免把不完整数据写成一条看似正常的回测记录。
