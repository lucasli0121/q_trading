# 检查报告：星级越界导致交易信号整条丢失（2026-10-12）

## 一、现象

`log/errors.log` 共 33 行，全部是同一类错误，集中在 10:24:00 至 10:26:02，共 **3 次请求**：

```
2026-10-12 10:24:00,387-api.client-250-ERROR: HTTP 400
  http://203.0.113.10:8000/api/trade_signal/add
  响应体: {"detail":"star 应在 0~5.0 之间"}
2026-10-12 10:24:00,387-workflow.strategy_workflow-2513-ERROR: 保存交易信号失败: Client error '400 Bad Request'
```

`log/info.log` 共 5180 行，ERROR 6 条（3 次请求 × 2 条：`api.client` 记 HTTP 响应、`strategy_workflow` 记异常栈），
**零 WARNING、零 CRITICAL**。也就是说整份日志里唯一的异常就是这一处，其余运行正常。

## 二、定位过程

### 1. 三条错误的发起方

失败路径不打印「交易信号已保存」（那行日志在 `add()` 成功之后），但每次调用前都会先打 `卖出信号计算`，
用它对齐时间即可还原是哪些信号：

| 错误时间 | 前置日志 | 股票 |
| --- | --- | --- |
| 10:24:00,387 | 10:24:00,366 卖出信号计算 | 600183.SH |
| 10:26:01,225 | 10:26:01,093 前后 | 600183.SH |
| 10:26:02,719 | 10:26:02,701 卖出信号计算 | 300857.SZ |

三条都是**波段策略的卖出信号**。

### 2. 对照案例：同一只票、同一天，未越界时正常

```
10:26:01,586 卖出信号计算: code=600183.SH, buy_price=130.53, sell_price=125.12, profit_rate=-4.14%
10:26:01,603 交易信号已保存: ... code=600183.SH, action=卖出, score=-9.75, star=4.9, ...
            reason=条件满足: 枢轴点分值:0.00, 布林带分值:-7.50, 平均分值:-3.75，持仓回撤-10.63%(...扣-6.00分)
```

`score=-9.75` → `star=4.9`，通过。而 10:24:00 与 10:26:02 的两条失败，
说明它们的 `score` 必然低于 **−10.0**（`star = |score| / 2 > 5`）。

需要说明的是：**这三条失败信号的具体分值没有落盘**，因为失败路径不打印分值与星级
（`交易信号已保存` 那行在 `add()` 之后）。上面的边界是从对照案例与下面的算式推导出来的，
不是观测值。

### 3. 边界推导

波段策略卖出分是三项叠加：

```
final_score = (枢轴点分 + 布林带分) / 2  +  持仓回撤扣分(-6.0)  [+  账户回撤扣分(-6.0)]
star        = -final_score / 2
```

日志里各分项实际取值范围：枢轴点分 ∈ {−5.00, 0.00, 5.00}，布林带分 ∈ {−7.50, −5.00, 0.00, 5.00, 7.50}。
于是位置分最低 = (−5 − 7.5) / 2 = **−6.25**，再叠回撤止损 −6.0 得 **−12.25**，
若账户回撤同时触发再减 6.0 得 **−18.25**。

`star` 相应为 **6.1** 或 **9.1**，双双越过服务端上限 5.0。

## 三、根因

两件事叠加：

**服务端新增了校验**（`q_trading_server/web_api/routers/trade_signal.py`）：

```python
MAX_STAR: float = 5.0

def _validate_star_value(star: float) -> float:
    if star < 0 or star > MAX_STAR:
        raise HTTPException(status_code=400, detail=f"star 应在 0~{MAX_STAR} 之间")
```

**本端波段策略卖出侧没有夹值**（`strategy/swing_trading_strategy.py` 原 733 行）：

```python
extra["star"] = round(-1.0 * final_score / 2, 1)   # 无 clamp
```

四种 star 折算里只有这一处漏了。其余三处都做了夹取：

| 位置 | 原实现 | 是否夹值 |
| --- | --- | --- |
| `strong_rebound_strategy.py` 买入 | `max(0.0, min(avg_score / 2.0, 5.0))` | 是 |
| `strong_rebound_strategy.py` 卖出 | `max(0.0, min(-score / 2.0, 5.0))` | 是 |
| `volume_expansion_strategy.py` `_to_star` | `max(0.0, min(score / 2.0, 5.0))` | 是 |
| `swing_trading_strategy.py` 卖出 | `-1.0 * final_score / 2` | **否** |

同一段折算逻辑在四个地方各写一遍，漏掉一处即出事。买入侧（`star = avg_score / 2`）同样没夹，
只是因因子分值上限恰好使 `avg_score ≤ 6.25`、`star ≤ 3.1` 而未暴露，属于同一类隐患。

## 四、影响

不只是「星级记错」。`workflow/strategy_workflow.py::_save_trade_signal` 里，
`add()` 位于 try 块开头，异常被 `except` 捕获后返回 `False`：

```python
try:
    self._trade_signal_api.add(...)          # ← 这里抛
    self.logger.info("交易信号已保存: ...")
    ... MQTT 推送 / 文本推送 ...              # ← 全部跳过
except Exception as exc:
    self.logger.error("保存交易信号失败: %s", exc, exc_info=True)
    return False
```

调用方 `_process_bar` / `_process_tick` 收到 `False` 即跳过订单创建。所以一次越界导致该条信号：

1. 不写库；
2. 不发 MQTT 实时流；
3. 不推送企业微信/短信；
4. **不创建卖出订单**。

跌得越深（越需要止损）的信号越容易越界，恰恰是被丢弃的那批。这与 2026-09-15 线上 422 的失效模式完全相同
（保存失败 ⇒ 整条信号连带下单一起消失），只是触发字段从 `reason` 换成了 `star`。

## 五、修法

### 1. 折算逻辑上移基类，消除四处重复

`strategy/base_strategy.py` 新增：

```python
STAR_MAX: float = 5.0

@classmethod
def score_to_star(cls, score: float) -> float:
    value: float = float(score or 0.0)
    if value != value:          # NaN：夹取对它无效
        return 0.0
    return round(max(0.0, min(abs(value) / 2.0, cls.STAR_MAX)), 1)
```

`abs(score)` 同时覆盖买入正分与卖出负分，两者口径本就一致（只差符号）。

五个调用点统一改写：`swing` 买入/卖出、`strong_rebound` 买入/卖出、
`volume_expansion`（`_to_star` 保留方法名，内部委托给基类，兼容既有调用点）。

### 2. API 边界再兜一次

`api/trade_signal.py` 新增 `_as_star()`，与既有的 `_as_text()` 同一层防御：
越界时**截断**并打 WARNING，不做符号翻转（负数说明上游算错符号，截成 0 而不是猜成正值）。

```python
if number < 0 or number > STAR_MAX:
    logger.warning("star 超出服务端允许范围 [0, %.1f]，已截断: 原值=%s", STAR_MAX, value)
return round(max(0.0, min(number, STAR_MAX)), 1)
```

理由是 `_as_text` 那条注释的同款逻辑：上游给脏值不该演变成「信号整条丢失」。
将来新增策略漏夹时，最坏结果是星级被截断 + 一条 WARNING，而不是信号消失。

### 3. 守卫测试

新增 `tests/test_star_range.py`（16 项）：

- `score_to_star` 边界逐点核对（−12.25 → 5.0、−10.0 → 5.0、−9.75 → 4.9、±0、NaN、None），
  以及 −100~100 全区间扫描断言输出恒在 [0, 5]；
- `_as_star` 的截断、取整、非法值回退，并端到端断言 `add()` 发出的请求体里 `star` 已在范围内；
- 用 mock 因子驱动**真实**卖出路径，构造 −12.25 与叠加账户回撤两个场景；
- **源码级守卫**：`strategy/` 下每个 `"star":` 产出点与 `star: float =` 赋值点都必须经过统一折算函数，
  防止将来新增策略又自己写一遍裸算式。

## 七、遗留与建议

1. **`_save_trade_signal` 的两条 False 路径语义混在一起**：「未达星级门槛」与「保存失败」都返回 `False`，
   调用方无法区分。按当前 fail-closed 口径，保存失败时不下单是保守选择，但这也意味着
   未来任何一次接口异常（网络、5xx、契约变更）都会静默停掉该信号的推送与下单，只留一条 ERROR 日志。
   若要区分，可让保存失败时返回一个显式的 `None` 或在调用方记一条更醒目的提示。
2. **部署**：生成机器上跑的是 PyInstaller 打包产物，本次修改需重新打包/部署才生效。
3. 本次只检查了用户提供的两个日志文件。`errors.log` 仅覆盖 10:24–10:26 这一窗口，
   若怀疑更早时间存在同类问题，可查服务端日志或历史归档。
