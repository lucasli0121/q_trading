# 交易信号保存 422 修复报告

**日期**：2026-09-15
**范围**：`q_trading_work`（策略引擎）本端
**现象**：线上持续报 `保存交易信号失败: Client error '422 Unprocessable Entity' for url '.../api/trade_signal/add'`
**结论**：**本端策略代码的一个「多写一个逗号」导致 `reason` 变成 tuple**，JSON 序列化成数组后被服务端 `str` 字段校验拒绝，整条交易信号（含 MQTT 推送与后续订单判定）被丢弃。与服务端契约变更**无关**。

---

## 一、排查过程（为什么不先怀疑服务端）

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 比对本端请求体 vs 服务端 `TradeSignalCreateRequest` | 字段名、类型、required（`strategy_id`/`stock_code`）**完全吻合**，契约没变 |
| 2 | 拉取运行实例 `/openapi.json`（`203.0.113.10:8000`）核对真实部署的 schema | 与仓库代码一致，`required=[strategy_id, stock_code]`，两者本端都传了 |
| 3 | 对真实实例做**字段类型矩阵探测**，抓 422 的响应体 `detail` | 定位到唯一可能的错误形态：`string_type`（str 字段收到 `null`/数组）与 `float_type` |

探测矩阵结论（真实实例实测）：

| 请求体变形 | 结果 |
|---|---|
| 正常体 | **200** |
| `reason=["a"]`（数组） | **422** `{"type":"string_type","loc":["body","reason"]}` |
| `reason=None` / `action=None` / `strategy_id=None` / `stock_code=1` | **422** `string_type` |
| `trade_price=None` | 422 `float_type` |
| `profit_rate="1.5"`（字符串数字）、多余字段 | **200**（数值会被强制转换） |

⇒ 即「某个字符串字段被传成了 None 或数组」。结合报错时间点（09:54/10:04/10:06，盘中），逐字段回溯 `_save_trade_signal` 的入参：

- `strategy_id` / `user_strategy_id`：实测 `/api/user_strategy/all` 返回均为 `str`（`_id` 十六进制），排除
- `stock_code`：`handle_bar`/`handle_tick` 均 `str(...)` 强转且过滤空值，排除
- `action`：由 `signal_type` 三元表达式生成，恒为 `str`，排除
- `trade_price` / `profit_rate`：均由 `float(...)` 产出，排除
- **`reason = extra.get("reason", "")`：唯一没有类型兜底的字段** ← 命中

### 根因

`strategy/swing_trading_strategy.py`（低频波段交易策略）卖出命中分支：

```python
extra["signal"] = "SELL"
extra["reason"] = (
    f"条件满足: 因子返回的分值满足卖出条件, 枢轴点分值:{inday_score:.2f}, 布林带分值:{boll_score:.2f}"
),     # ← 多余的逗号：把 str 变成了单元素 tuple
```

Python 里这是**合法**代码，只是类型从 `str` 变成 `tuple`。于是：

1. `TradeSignalApi.add` 把 `("...",)` 放进 JSON 请求体 → 序列化成 `["..."]`；
2. 服务端 `reason: str` 校验失败 → **422**；
3. `_save_trade_signal` 的 `except` 只记录「422 Unprocessable Entity」，**不打印响应体** → 日志看不出是哪个字段；
4. 该函数返回 `False` → `_process_bar` / `_process_tick` 直接 `return`，**MQTT 推送与订单创建判定一并被跳过**。

> 影响面：只有**波段交易策略的卖出信号**受影响（强趋势策略的 `reason` 写法正确）。买入信号与另外两个策略不受影响。

## 二、改动明细

| # | 文件 | 改动 | 目的 |
|---|---|---|---|
| 1 | `strategy/swing_trading_strategy.py` | 删除多余逗号 | **修掉根因** |
| 2 | `api/trade_signal.py` | 新增 `_as_text()`，`add()` 对 5 个 str 字段归一化 | API 边界兜底，脏值不再变成 422 |
| 3 | `workflow/strategy_workflow.py` | `_save_trade_signal` 对 `reason` 做类型兜底 | 日志与 MQTT 载荷保持文本类型 |
| 4 | `api/client.py` | 新增 `_log_error_body()`，非 401 的 4xx/5xx 打印响应体 | **可观测性**：下次 4xx 自解释 |

### 2.1 `api/trade_signal.py` — API 边界归一化

```python
def _as_text(value: Any) -> str:
    """None → ""；str 原样；tuple/list → 用 ", " 连接；其他 → str(value)"""
```

`add()` 中 `strategy_id` / `user_strategy_id` / `stock_code` / `action` / `reason` 统一走 `_as_text`。
好处：**一个上游脏值不再让整条交易信号丢失** —— 这正是本次故障的放大机制。

### 2.2 `api/client.py` — 错误自解释

```python
# 其余 4xx/5xx：把响应体写进日志。
# 否则上层只能看到 "422 Unprocessable Entity"，完全不知道是哪个字段不合格
self._log_error_body(e)
raise
```

输出形如：`HTTP 422 http://.../api/trade_signal/add 响应体: {"message":"参数错误","errors":[{"type":"string_type","loc":["body","reason"],...}]}`
（截断 500 字符；401 分支逻辑不变）

## 四、遗留与建议

1. **服务端无信号删除接口以外的清理能力**：本次探测记录已用 `DELETE /api/trade_signal/{id}` 清理干净。
2. **同类写法已全仓库静态清零**：AST 守卫当前覆盖 5 个目录，扫描结果为空；建议后续新增目录时同步加入 `SCAN_DIRS`。
3. **建议排查同源的「静默类型错误」**：本 bug 之所以难查，是因为 Python 不报错、单测不覆盖、日志不显示响应体。`api/client.py` 的响应体日志已在本次补上，后续 4xx 可直接定位字段。
