## 二、A：服务端取数与 3 个月保留窗口（实测数据）

在容器内直连生产服务端探测日K覆盖度（只读）：

| 代码 | 区间 | 实际返回 |
|---|---|---|
| `000001` | `2026-03-01 ~ 2026-07-31` | **仅 2 根**（`2026-07-15`、`2026-07-31`） |
| `000001` | `2026-08-01 ~ 2026-09-12` | 30 根（`2026-08-03 ~ 2026-09-11`） |
| `600519` | `2026-08-01 ~ 2026-09-12` | 0 根 |
| `600519` | `2026-06-01 ~ 2026-09-12` | 0 根 |
| `002415` | `2026-08-01 ~ 2026-09-12` | 0 根 |

与你说明的机制吻合：**超出保留窗口的历史被清理**，且不在库中的标的会即时回源第三方
（`600519`/`002415` 当前取不到，即回源失败或超时）。由此带来的两点后果：

1. 旧的真实数据用例用了 `2026-03-01 ~ 2026-07-31`（已滑出保留窗口）→ 恒定 0 交易，
   这**不是代码缺陷**。已把该用例改为近 1 个月区间（`2026-08-01 ~ 2026-09-12`），
   现在**已通过**。
2. 「取数失败」和「该股在库里就是没有」在**HTTP 层面无法区分**，所以本端只对
   「接口抛异常」判定为取数失败；接口正常返回空列表仍按「无数据」处理（不做无限重试）。

## 三、B：可观测性改造

### 3.1 新增异常类型 `MarketDataFetchError`（`strategy/base_strategy.py`）

语义：**「这次没取到」≠「该股没有行情」≠「不符合策略条件」**。实时链路不得静默忽略，
回测链路必须中止。

### 3.2 `load_his_daily_data` 改造

| 项 | 改造前 | 改造后 |
|---|---|---|
| 取数异常日志级别 | `logger.debug`（线上等于没有） | `logger.warning`，含 **code / 区间 / 尝试次数 / 原始异常**，并显式声明「这是取数失败，不是无数据，不得当作正常不满足条件忽略」 |
| 失败返回值 | 普通空表 | 空表 + `df.attrs["fetch_failed"]=True` / `attrs["fetch_error"]`（用 pandas 官方元数据容器，**不污染列结构**，下游因子不受影响） |
| 重试 | 无 | `retries` / `retry_interval`，可用类属性 `FETCH_RETRIES` / `FETCH_RETRY_INTERVAL` 配置；**实时链路默认 0 次重试**（盘前选股不能 sleep 阻塞行情派发） |
| 失败是否上抛 | 从不 | `raise_on_error=True` 抛 `MarketDataFetchError`（回测用） |
| 日期参数 | 恒定带 `start`/`end` | 不变，并加了守卫测试（服务端不带日期必 500） |

### 3.3 `select` 结果契约（新增三个字段）

| 字段 | 含义 |
|---|---|
| `score` | 策略打分，取 `extra["score"]`，缺失/非法记 `0.0`（供保存选股结果使用） |
| `fetch_failed` | `True` **仅当取数失败**（接口异常且重试后仍失败）→ 该股**是否满足条件未知**，候选集不完整 |
| `reason_code` | `matched` / `not_matched` / `no_data` / `fetch_failed` / `strategy_error` |

`extra` 保持原样，向后兼容。

### 3.4 工作流（`workflow/strategy_workflow.py`）

- 盘前筛选把取数失败的股票**单独统计并 warning 告警**（列出代码，提示「非不满足条件、候选集不完整」）；
- 完成日志变为：`筛选 N 只, 符合策略 M 只, 取数失败 K 只`。

⇒ 「静默 0 交易」不再可能：要么有命中，要么日志里明确写出「K 只取数失败」。

## 四、C：回测数据完整性（fail-closed）

### 4.1 统一重试入口 `BacktestEngine._call_market_api()`

- 重试 `BacktestConfig.fetch_retries`（默认 **2**）次，间隔 `fetch_retry_interval`（默认 1s）；
- 重试期间逐次 warning，穷尽后 **抛 `MarketDataFetchError`**（错误消息含描述、尝试次数、原始异常）；
- 接口正常返回空列表 → **不重试、不抛错**，按「无数据」处理。

### 4.2 三处取数全部走该入口

| 位置 | 行为变化 |
|---|---|
| `_fetch_stock_data`（候选股 K 线） | 原 `except → 返回空表`（静默）→ 重试后仍失败**抛错中止** |
| `_fetch_benchmark_data`（基准） | 同上；且 `benchmark_code` **默认改为 `""`**（基准关闭） |
| `_select_candidates`（调策略 select） | 以 `raise_on_error=True` 调用；`MarketDataFetchError` **直接上抛**（不再回退「全量股票池」）；其他异常仍保留宽返回容错 |

### 4.3 `run()` 中止时**不写库**

`MarketDataFetchError` 在 `run()` 里捕获后记 error 再上抛 —— `save_results()` 根本不会被调用，
因此**不会留下一条看似正常的残缺回测记录**。

### 4.4 附带修正

1. `benchmark_code` 默认由 `"000300"` 改为 `""`：服务端日K不支持指数代码（P1-27），
   默认填代码只会取数失败；且与新规则叠加会导致默认配置直接中止。现与
   `TradeManager.DEFAULT_BENCHMARK_CODE` 口径一致。CLI `--benchmark` 默认同样改为空。
2. `_select_candidates` 里 `if "reason" in result` 恒为 `False`（`reason` 实际在 `extra` 里）
   → 复核日志全丢，已修正为从 `extra` 取。
3. `_run_minute_for_stock` 的兜底 `except Exception` 会吞掉 `MarketDataFetchError`，
   已加显式 `except MarketDataFetchError: raise`。
