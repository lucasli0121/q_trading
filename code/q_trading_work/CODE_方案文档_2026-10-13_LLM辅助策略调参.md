# LLM 辅助策略调参：可行性与落地方案（2026-10-13）

## 一、结论

接入大模型这条路可以走，但「把策略特征发给 DeepSeek，按返回分值调整权重」这个具体做法不可行。

不可行的原因不在模型能力，在于产出无法验证与复现。可行的形态是分工：LLM 负责读回测结果、写失效归因、提参数假设；数值搜索交给本地的确定性程序，因为回测引擎本身就是现成的目标函数。

在此之前还有一件更优先的事：当前的评估口径不足以支撑任何形式的调参。这一项不解决，无论用大模型还是用网格搜索，搜出来的都是噪声。

## 二、现状核查

### 2.1 可调参数的规模

| 位置 | 数量 | 说明 |
| --- | --- | --- |
| `cfg/strategy.yaml` | 42 个数值标量 | 各策略分项分值、阈值、窗口、权重 |
| `factor/` 内部 | 约 40 处分值档位 | 16 个因子的硬编码打分档位 |
| 少量权重 | 4 个 | `buy.volume_weight`=0.6、`buy.partner_weight`=0.4（yaml 可配）；`BUY_VOLUME_WEIGHT`=0.7、`BUY_TREND_WEIGHT`=0.3（类属性，不可配） |

参数来源三级：类属性、`cfg/strategy.yaml`、服务端模板。实盘是「择一」，`strategy_params` 非空时模板被整体忽略。

### 2.2 是否具备参数寻优能力

源码内检索 `optuna`、`grid_search`、`param_search`、`hyperopt`，零命中。当前所有参数均为人工设定。

### 2.3 现有回测结果的横向对比

同一回测窗口（2026-07-21 至 2026-10-08）、同一策略（成交量放大）、同一 6 只持仓池、同为分钟频，只改过滤与资金分片参数：

| 配置 | 笔数 | 胜率 | 总收益 | 最大回撤 | 成交交易日 |
| --- | --- | --- | --- | --- | --- |
| 基线 | 413 | 11.27% | −94.43% | 94.43% | 17 |
| +30 分钟成交间隔 | 79 | 24.05% | −24.60% | 24.60% | 16 |
| +间隔 +资金分片 | 57 | 24.56% | −11.96% | 11.96% | 15 |
| 单只 000988.SZ | 36 | 16.67% | −15.53% | 21.59% | 5 |

两组结论同时成立：参数对结果的影响极大（−94% 与 −12% 的差距来自三个参数）；四组全部为负，说明信号本身没有正期望。

### 2.4 回测成本口径

`backtest/main.py` 默认值：

| 参数 | 默认值 | 单位 |
| --- | --- | --- |
| `--buy-slip` | 0.2 | 元（绝对值） |
| `--sell-slip` | 0.2 | 元（绝对值） |
| `--fee-pct` | 0.02 | 百分点（万二），买卖双向各收一次 |
| `--fee-low` | 5.0 | 元 |

两处与实盘不一致：

1. 滑点按绝对金额计（成交价 = 基准价 ± 0.2 元）。在 10 元股票上折算 2%，在 100 元股票上折算 0.2%。实盘成本是按比例计的，这里口径不统一。
2. 无印花税项。检索 `stamp`、`印花税` 均零命中。A 股印花税为卖出单边 0.05%，每笔卖出被少算约 0.05%。

## 三、阻碍调参的四项前置缺陷

### 3.1 目标函数随数据增长漂移

回测直接向服务端取数，服务端日 K 每日增长。`--start` 与 `--end` 完全相同的一条命令，实测得到过 18 笔 +11.32%、28 笔 +5.52%、39 笔 −9.16% 三种结果（分别为不同日期运行的快照，已用 `git stash` 排除代码因素）。

后果：今天搜出的最优参数，下周不再是最优，因为目标函数已经变了。

修法：行情先落盘为快照（按 code、频率、时间范围存本地文件），回测改为从快照读取。快照一旦固定，结果永远可复现。

### 3.2 日频回测不产生卖出信号

`backtest/backtest_engine.py` 中已有明确注释：卖出侧只有分钟频有信号，日频是「持有 N 日到期」的固定卖出，不产生信号，因此 `sell_score` 与 `sell_star` 恒为 0.0。

后果：`sell.max_score`、`sell.drawdown_pct`、`sell.drawdown_score` 在日频回测中完全不参与决策。搜索这些参数得到的是纯噪声，而且日志与汇总都不会提示这一点。

修法：参数搜索一律使用 `--frequency minute`，不接受日频结果作为调参依据。

### 3.3 样本量与参数数量的比例失衡

现有最好的一组：57 笔成交，分布在 15 个交易日，涉及 6 只股票。待调参数 42 个。

后果：平均每个参数对应 1.4 笔成交。这个比例下，搜索过程必然把 2026 年 7 月至 10 月这段特定行情拟合进去，样本外不会成立。

修法：切分样本内与样本外（例如前 2/3 调参、后 1/3 只做验证）；一次同时调整的参数不超过 3 到 5 个；在一个参数上得到稳定结论后再动下一个。

### 3.4 当前所有配置均为负收益

见 2.3，四组结果全部为负。

后果：如果毛期望不足以覆盖成本，精调权重只能改变亏损的速度，不能改变方向。此时接大模型是在给一个负期望体系做微调。

修法：先做成本敏感性分析。测出两个数：扣成本前的毛收益是多少；单笔平均盈利需要达到多少才能盈亏平衡。这两个数决定了后续该继续调参还是重新设计信号。

## 四、LLM 的适用边界

| 场景 | 是否适合 | 原因 |
| --- | --- | --- |
| 输出分值权重数值 | 否 | 不受目标函数约束，输出的是语义上合理的编造值；同输入不同输出，无法归因与回滚；对 0.6 与 0.65 的差别无可靠感知 |
| 回测明细归因 | 是 | 明细已含 `buy_score`、`buy_star`、`sell_score`、`sell_star` 与 `reason` 文本；几百笔的失效规律人工逐条读不出来 |
| 生成候选参数区间 | 是 | 给区间与理由，由本地搜索验证，不承担定值责任 |
| 异常诊断 | 是 | 日志、契约错误、参数不一致的排查速度快于人工 |
| 直接写回 yaml 或服务端 | 否 | 参数有三处真源，自动写回会破坏可追溯性 |

使用 LLM 时有一条硬约束：它只产出候选，不产出结论。候选必须经过本地回测验证与人工确认才能生效。

## 五、落地路线

### 阶段一：评估基线

不改策略代码，只改评估方式。

- 行情落盘为快照，回测从快照读
- 固定回测口径：`--frequency minute`，成本参数按实盘真实口径补齐（含印花税）
- 加入样本内与样本外切分
- 产出：一份可复现基线，记录完整 config、快照标识、代码 commit

验收标准：同一条命令在任何时间重跑，笔数与收益完全一致。

### 阶段二：确定性参数搜索

- 从 42 个标量中选 3 到 5 个关键项，建议候选：`sell.max_score`、`sell.drawdown_pct`、`buy.min_score`、`match.volume_score`、`min_trade_interval_minutes`
- 网格或随机搜索，目标函数取样本内收益与回撤的组合
- 样本外只做验证，不参与选择

产出：参数敏感度表，标明哪些参数改动后结果无变化（这类参数不值得继续投入）。

验收标准：样本外结果与样本内方向一致。不一致即判定过拟合，该组参数作废。

### 阶段三：LLM 接入

- 归因：读取聚合统计，输出失效模式
- 假设：输出候选参数区间与理由
- 产物落盘为待审文件，人工确认后才写回配置

## 六、DeepSeek 接入的接口形态

### 6.1 输入

不要直接传原始明细。一次回测几百条，聚合后信息量不降反升，且省去上下文与费用。

建议输入三个部分：

1. 按 (code, 信号方向, 星级分档) 聚合的统计：笔数、胜率、平均盈亏、平均持仓时长
2. 按交易日的分组统计，附当日市场涨跌
3. 亏损最大的 20 笔的 `reason` 文本

### 6.2 输出 schema

```json
{
  "findings": [
    {"pattern": "描述", "evidence": "对应统计", "affected_trades": 12}
  ],
  "hypotheses": [
    {"param": "sell.max_score", "current": -6.0,
     "to_range": [-8.0, -10.0], "reason": "依据"}
  ],
  "confidence": "low"
}
```

约束：

- 只输出区间，不输出精确值
- 每条 finding 必须带 evidence，指向具体统计
- schema 校验不通过即丢弃，不降级使用
- 记录 prompt、模型名、原始响应到文件，保证可追溯
- 任何参数改动必须经人工确认

### 6.3 成本

归因单次输入在数千 token 量级，费用可忽略。若改为传入原始明细，单次成本上升一个量级且效果更差。

## 七、风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 过拟合 | 主要风险。57 笔成交拟合 42 个参数 | 样本外验证，限制同时调整的参数个数 |
| LLM 输出漂移 | 同 prompt 不同结果 | 只用它提假设，不用它定值 |
| 口径漂移 | 日频与分钟频的卖出逻辑不同 | 统一使用分钟频 |
| 合规 | 系统定位为辅助决策工具 | 对外不表述为「AI 调参提升收益」 |

## 八、不建议做的事

1. 让 LLM 输出可直接写入配置文件或服务端的参数值。
2. 在日频回测上做参数搜索。
3. 在样本外验证之前宣布某组参数更优。
4. 用同一份数据既调参又验证。
5. 在缺少成本敏感性分析的情况下精调权重。
6. 依赖单次回测的数字作为结论。同一份配置因服务端日 K 持续增长，实测由 18 笔 +11.32% 变化到 39 笔 −9.16%（快照时点不同，非代码差异）。
