## 二、批次 A：缓存层重构

### A1 新增 `core/user_strategy_cache.py` — `UserStrategyCache`（单例）

职责（原 `base_strategy` 中的全局缓存全部迁入）：

| 缓存 | key | 写入方 | 读取方 |
|---|---|---|---|
| 当日分钟行情 | `bar:{code}:{day}` | **workflow（唯一写者）** | 各策略 |
| 策略打分 | `score:{user_strategy_id}:{code}:{action}:{day}` | 各策略 | 各策略 |
| 选股结果 | `select:{user_strategy_id}:{day}` | workflow 盘前选股 | 各策略 |

要点：
1. **双重缓存**：进程内快照（`dict`）+ Redis。读优先内存，内存未命中才读 Redis 并回填；写同时更新两者。
2. **写保护**：全局 `RLock` 保护内存字典与 Redis 失败标记。
3. **行情缓存由 workflow 单点写入**，策略侧不再写 → 彻底消除「N 个用户把同一根 bar push N 次」的 P0-4 污染。
4. 读取函数带长度参数：`get_minute_bars(code, length=0)`，`length<=0` 表示当日全量。
5. 内存快照按数量裁剪（`MAX_MINUTE_CACHE=240`，覆盖整个交易日）。
6. 提供 `clear_user(user_strategy_id)` / `clear_day(day)` 供盘前清理。

### A2 `base_strategy.py` 瘦身

- **删除**：`_minute_cache` / `_minute_cache_day` / `_stock_scores` / `_redis_enabled` / `_redis_failed`
  / `_save_minute_cache` / `_minute_cache_key` / `_get_minute_cache` 内部实现；
  `_save_score_cache` / `_get_score_cache` / `_cache_score_key` 内部实现。
- **保留同名薄封装**（子类调用点不动）：
  - `_get_minute_cache(code, length=0)` → `cache.get_minute_bars(code, length)`
  - `_get_score_cache(code, action, create_time)` / `_save_score_cache(...)` → 带 `self.user_strategy_id`
  - `_load_select_stocks(today_str)` → 改走缓存 `select:{user_strategy_id}:{day}`（P2-25：N 用户不再 N 次请求）
- `base_strategy` 不再直接持有 Redis 开关与失败标记。

### A3 子类适配

- `strong_rebound_strategy._before_minute_route` / `swing_trading_strategy._before_minute_route`：
  **移除 `_save_minute_cache` 调用**（改由 workflow 统一写入）。
- `swing_trading_strategy._save_sr_points` / `_get_sr_points`：key 由
  `{strategy_name}:sr_points:{code}` 改为 **`{strategy_name}:sr_points:{user_strategy_id}:{code}`**（P1-9）。

### A4 workflow 写入行情

- `handle_bar` 循环内、`submit` 之前调用 `UserStrategyCache.push_minute_bar(code, bar_data)`（**每 code 一次**）。

## 四、批次 C：TradeManager

| 条目 | 落地要点 |
|---|---|
| P0-26 | 买入手续费计入成本：`position_price` 保持成交价（不含费），另将买入费累加进持仓成本字段；`remaining_cash` 与 `_calc_available_cash` 统一改为「初始资金 + 已实现盈利 − 持仓成本 − 买入费累计」，保证三处一致 |
| P1-27 | 补 `execution_days = 交易日历差(start_date, today) + 1`；`annualized_return_rate = (1+r)^(250/days) − 1`；`benchmark_return_rate` 接沪深 300 同期涨幅（取不到时保持原值） |
| P1-28 | 生成执行记录时按最新行情刷新**全部**持仓的 `current_price`（复用分钟行情快照，取不到则保留原值并标注「按上次成交价估算」） |
| P1-16 | `save_execution` 失败 → 有限次重试 + 落盘补偿队列（`log/pending_execution.jsonl`），进程启动时尝试补投 |
| P1-17 | **补充方案**：客户端生成 `client_order_id = {user_strategy_id}:{code}:{action}:{yyyyMMddHHmmss}:{uuid4前8位}`，随订单一起提交；服务端若未支持该字段则客户端按 `client_order_id` 做本地去重（记录近期已提交键），避免超时后重复 POST |
| X3 | T+1 可卖数量：持仓增加 `t1_qty`（当日买入未可卖数量）与 `t1_day`；`_create_sell_order` 卖出数量改为 `quantity − 今日买入数量`，为 0 时跳过下单（信号照旧发出） |

> X3 语义确认：昨天买入 A、今天再买 A → 今天卖出信号只卖**昨天那部分**；仅今天买入 → 今天不可卖。

## 七、需要负责人确认的问题（不阻塞开工）

1. **P1-17 服务端是否支持幂等键**：若服务端可加 `client_order_id` 唯一索引，方案最稳；否则只能本地去重（跨进程/重启仍可能重复）。
2. **X2**：计划已明确「推送的应是用户股票池内的股票」。现状代码在 `_save_trade_signal` 之后才过滤股票池，
   即**已写库+已推送**后才判断池子。确认后我将把股票池/黑名单过滤前移到信号写入之前
   （与「多出信号」目标不冲突：不在池内的股票本就不是给该用户的信号）。
3. **X3 的 `t1_qty` 需要新增持仓字段**（服务端 `positions` 为自由数组，已确认可存额外键）。
   如服务端对 `positions` 元素做严格校验，需要服务端同步放行。
4. **P0-26 买入手续费口径**：方案采用「成本含买入费」，会影响历史盈亏对比（旧记录不含费）。
   如需从某日起生效，请给一个生效日期。
