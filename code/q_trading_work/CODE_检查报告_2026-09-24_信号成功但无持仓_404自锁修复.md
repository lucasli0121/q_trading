日期：2026-09-24
输入：部署设备 `log/errors.log`、`log/info.log`、`log/errors.log.2026-09-22`、`log/info.log.2026-09-23`

## 三、根因：一个自锁

```
服务端 /api/user_strategy/{id}/execution/latest → 404（该策略还没有任何执行记录）
  → UserStrategyApi.get_latest_execution 抛出 httpx.HTTPStatusError
  → workflow._load_positions 捕获后返回 None（P1-18 fail-closed）
  → _process_bar / _process_tick 判定「持仓未知」，跳过下单
  → 执行记录的唯一来源是订单成交后由 TradeManager 写入
  ⇒ 永远没有执行记录 ⇒ 永远 404（新策略下不了第一单）
```

P1-18 的 fail-closed 本身没错，错在**把「无执行记录」与「取数失败」混为一谈**：

- 「读不到持仓」→ 不能当成「无持仓」（否则重复买入）——这才是 fail-closed 要防的；
- 「服务端明确回答没有记录」→ 就是「无持仓」，应当放行下单。

同一份数据在另一处却被当成正常状态：`_load_execution_data`（启动时加载执行数据）对例外一律兜底并继续运行，而 `_load_positions`（下单前判定）却 fail-closed。两处行为相反，这是缺陷的直接来源。

---

## 四、修复

原则：**API 层负责把「404 = 无数据」与真实故障区分开，fail-closed 只对真实故障生效。**

| 文件 | 改动 |
|---|---|
| `api/client.py` | 新增 `is_not_found(exc)` 判定 HTTP 404（不改 `_handle_response` 控制流，异常照旧上抛） |
| `api/user_strategy.py` | `get_latest_execution`：404 → 返回 `{}`（= 无执行记录 = 空持仓），日志 DEBUG；500/超时/连接失败照旧上抛 |
| `api/trade_signal.py` | `latest`：404 → 返回 `{}`（「查无此信号」是首次买入前的正常状态），消除 `查询最近买入记录失败` 的 warning + 堆栈噪音 |
| `workflow/strategy_workflow.py` | `_load_positions` 明确三分语义（无记录 `{}` / 取数失败 `None` / 正常）；首次发现「尚无执行记录」记一条 INFO；`_load_execution_data` 真实故障 DEBUG → WARNING |
| `workflow/strategy_workflow.py` | 「信号已记录但没下单」的 5 类阻断原因 DEBUG → INFO（见第六节），`_process_tick` 补齐同样的分支日志 |
| `trade/manager.py` | `_update_strategy_execution` 取数失败 DEBUG → WARNING（见第七节） |

`_process_tick` 的判定分支同时重写为与 `_process_bar` 相同的嵌套结构（控制流等价），使两条链路的下单/跳过日志一致、便于比对。

## 六、附带发现 1：`max_stock_count = 0` 的语义与文档冲突（需你决策）

`6a58d62b28893aa08c3ed4df` 的 `max_stock_count = 0`、`initial_amount = 0`，实测 9 条信号 / 0 条订单。即使修好第三节的自锁，它仍会被拦下：

```python
# workflow._parse_max_stock_count 的 docstring
# `-1`（或任何负数）= 不限制持仓数量；`0` = 不允许新建持仓；正数 = 持仓上限
# -> _is_position_limit_reached: limit=0 => len(positions) >= 0 恒为 True
```

但另外三处的文档都写着 **0 = 不限制**：

- `code/q_trading_work/api/user_strategy.py:59`
- `code/q_trading_cli/api/user_strategy.py:63`
- 服务端 `models.py`：`max_stock_count: int = Field(default=0, description="最大持仓数量")`（未定义 0 的含义）

`CODE_REVIEW_2026-09-12.md` 的 P0-6 条目原意也是「`0` 不再被改写成 4」，即认可 0 是「不限制」。

**风险**：任何未显式设置该字段的策略（服务端默认 0）会被静默禁止建仓。CLI 创建对话框预填 4，所以走 UI 创建的策略不受影响；`6a58d62b…` 是 0，需要确认它的期望语义。

**需要你决定**：`0` 到底是「不限制」还是「不允许新建」，以及是否统一收敛到一处解析（建议 `-1`/负数 = 不限制，`0` = 不允许，并在服务端/CLI 文案同步）。本次**未改**这个语义。

该策略的 `initial_amount = 0` 也需要确认——按现有口径它的可用资金为 0，`_calc_buy_quantity` 会直接返回 0。

## 七、附带发现 2：TradeManager 取数失败会截断持仓（需你决策）

`trade/manager.py::_update_strategy_execution` 用最近一条执行记录里的 `positions` 作为基础，再叠加本次成交：

```python
exec_data = {}
try:
    exec_data = self._user_strategy_api.get_latest_execution(user_strategy_id)
except Exception:
    self.logger.debug("加载最近执行记录失败 …")   # 原为 DEBUG，已被吞
...
if exec_data:
    execution.from_db(exec_data)
```

取数失败（超时/5xx）时 `exec_data` 为空 → 新写出的执行记录**只剩本次成交的持仓**，其余持仓从记录里消失。之后 `_load_positions` 读到的是被截断的记录，可能因此重复买入或漏卖。

本次只把日志从 DEBUG 提到 WARNING（含「已有持仓可能丢失，请对账」字样），**未改控制流**。可选的处置方向：

1. fail-closed：读不到旧记录就**不写**新记录（宁可账目滞后，也不写残缺记录）；
2. 或从订单流水重建持仓（`/api/order/list/{user_strategy_id}` 已是完整来源），彻底不依赖「最近一条执行记录」。

需要你定方向，我再改。另：本次修复后，404（无记录）不再抛到这里，这个分支只剩真实故障会命中。
