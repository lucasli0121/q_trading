### 2. P1-17：本地订单幂等加固（跨重启）

`trade/manager.py`

- 新增 `SUBMITTED_ORDER_KEYS_FILE = "log/submitted_order_keys.jsonl"`。
- 启动时 `_load_submitted_order_keys()`：从文件恢复 TTL（24h）内的幂等键，
  损坏行/过期行自动跳过，文件不存在不影响启动。

⚠️ 仍存在的边界：服务端不做去重，所以**同一秒内**通过多个实例（多进程部署）下单仍可能重复；
当前是单实例部署，可接受。若将来多实例，需要服务端支持幂等键或引入共享存储（Redis）。

### 3. P1-27：基准收益率降级处理

`trade/manager.py` + `cfg/stock.cfg`

- `_resolve_benchmark_return_rate`：
  - `[benchmark] code=` 置空 → **主动关闭**基准计算（不发请求）；
  - 取数异常 / 数据不足 2 根 → 记 **warning**（说明服务端日K暂不支持指数代码、可换 ETF 代理），

## 四、P0-26 口径说明（回答「需要进一步解释」）

### 1. 改前是什么口径

原 `_apply_order_to_positions` 买入时：

```
cost_price = (成交金额 + 手续费) / 数量      # 手续费被摊进了「成本价」
```

所以资金公式 `剩余资金 = 初始资金 + 已实现盈利 - Σ(数量 × 成本价)` 是**间接**把手续费算进去的。
副作用：持仓收益率的成本基准被手续费稀释（比如 10000 元的持仓，5 元手续费让成本价虚高 0.05%）。

### 2. 改后是什么口径（P0-26）

```
cost_price = 纯成交均价            # 成本价 = 真成交价，更符合常规含义
持仓.fee   = 累计买入手续费         # 手续费单独存放
剩余资金   = 初始资金 + 已实现盈利 - Σ(数量 × 成本价) - Σ(持仓累计 fee)
```

卖出时按卖出比例释放对应手续费，并从已实现收益中扣掉（买入费 + 卖出费都体现在最终盈亏）。
三处口径统一：`TradeManager._refresh_execution_metrics`、
`StrategyWorkflow._calc_available_cash`、服务端返回的 `remaining_cash`。

### 3. 我原先担心的「一次性下调历史 remaining_cash」

担心的是：服务端**已有持仓**若是旧口径（`cost_price` 含费、`fee` 为 0/缺失），
新代码若再额外减一次 `fee`，历史 `remaining_cash` 会突然变小。

### 4. 复核代码后的结论：**不会发生，也不需要数据修正脚本**

| 持仓来源 | `cost_price` 是否含费 | `fee` 字段 | `Σ(qty×cost) + Σfee` | 与旧公式比较 |
|---|---|---|---|---|
| 旧数据（本功能上线前买入） | 含（旧代码就这么存的） | 0（新字段空值） | `Σ(qty×cost)` | **完全等价，数值不变** |
| 新数据（上线后买入） | 不含 | 有值 | 实际占用资金 | 数值正确 |

两类互斥，**不存在重复扣费**，也不存在漏算；跨新旧加仓/卖出的两条路径我也逐条核对过，
释放手续费与已实现收益的加减是对称的。

### 5. 唯一残留差异（不是 BUG，是展示层）

老持仓的成本价含费、新持仓不含费，若前端把 `cost_price` 直接当「成本价」展示，
新旧混排时同一列含义略有差异（金额级别通常是千分之几）。处理方式二选一：

1. **不处理**（推荐，零风险）：等老持仓自然清仓后口径自动统一；
2. 严格一致：需要服务端提供历史买入手续费做一次性迁移——通常拿不到，还可能引入新的口径错误。

### 6. 需要你确认的 1 个点 ⚠️

**服务端在新增 `fee` 字段时，是否对历史持仓做了回填（从历史订单重算手续费）？**

- 若**未回填**（历史行 `fee` 为空/0）→ 现状即正确，**什么都不用做**（我判断是这个）；
- 若**已回填**→ 老持仓的手续费会被算两次（一次在老 `cost_price` 里，一次在新 `fee` 里），
  这才需要一次性数据修正脚本。
