## 一、结论

上一轮给波段策略加的 7 个参数（`match.trend_*` / `sell.drawdown_*` / `risk.*`）
已同步到服务端 **3 处**：策略模板 1 个 + 用户策略 2 个。回读校验逐字段通过。

同步过程中发现一个此前被忽略的问题：**只同步模板并不能让实盘生效**。原因是参数三级
回退是**择一**而非逐字段合并 —— 用户策略一旦配了 `strategy_params`，模板的
`default_params` 对它完全不生效，模板里的新字段也取不到。上一轮报告里「实盘靠类属性兜底
会生效」的说法在行为上是成立的，但那只覆盖了「值对不对」，没覆盖「界面上看不看得见」。

---

## 二、起因：择一语义让模板同步失效

`BaseStrategy._apply_resolved_params`（`strategy/base_strategy.py:240-250`）：

```python
if isinstance(user_strategy_params, dict) and user_strategy_params:
    params = user_strategy_params          # ← 非空则独占，模板被整体忽略
elif isinstance(default_params, dict) and default_params:
    params = default_params
else:
    params = self._load_yaml_params()
```

是三选一，不是逐字段覆盖。因此「补模板」这条路对带 `strategy_params` 的用户策略无效。

实测两个波段用户策略的原有配置都只有 3 个节、4 个字段：

```json
{"match": {"sr_window": 10, "sr_tolerance": 0.02},
 "buy":  {"buy_sr_window": 10},
 "sell": {"sell_sr_window": 10}}
```

缺的 7 个字段不会去模板取，而是由 `apply_params` 的 `params.get(key, 类属性)` 回退到
**类属性**。实测确认回退值正确（见第六节），所以**策略行为一直是对的**；
代价是这 7 个参数在服务端界面上看不到、也调不了，同时「三处一致」这条不变量被破坏。

## 四、代码改动

### 1. `api/user_strategy.py` — `update()` 补 `strategy_params` 入参

服务端 `UserStrategyUpdateRequest` 一直有 `strategy_params` 字段（"策略运行参数"），
本端 `update()` 没暴露，导致**本端没有任何通道能改用户策略的参数**。
本次补上，语义与其他字段一致（`None` 表示不修改）。

### 2. 新增 `sync_strategy_template_params.py` — 可复用的同步工具

参数三处一致这条不变量，①②（类属性 ↔ `cfg/strategy.yaml`）已由
`tests/strategy/test_param_defaults_consistency.py` 守住；③ 在服务端，本端测试够不着，
只能手动对齐。本次把它做成脚本，避免下次改参数时第三次手工维护而再次分叉。

设计要点：

- **值取自 `cfg/strategy.yaml`，不硬编码**。硬编码的值会在下次改参数时第二次分叉。
  脚本只硬编码 `desc`（纯展示，与策略行为无关）。
- **默认「补缺」不「覆盖」**（2026-09-29 当日修订，见第八节）：服务端已有字段保留原值，
  只补缺失字段，界面上调过的参数不会被冲回代码默认值；要主动拉齐需显式 `--align-values`。
- **默认 dry-run**，写入需显式 `--yes`。
- **传合并后的全量字段**，不依赖服务端合并语义（理由见第三节）。
- **本端未定义的服务端字段原样保留**，仅打印提示。
- **写入后回读校验**：字段齐全 + 本次写入值与目标一致，不通过则返回非 0 退出码。
- **`--scope all|template|user`**，默认两处都同步。

```bash
# 查看差异（只读）
docker exec q_trading_work python sync_strategy_template_params.py --strategy swing

# 实际写入
docker exec q_trading_work python sync_strategy_template_params.py --strategy swing --yes
```

需要 `cfg/stock.cfg [server] admin_token`。

### 3. 新增 `tests/test_sync_strategy_template_params.py` — 离线守卫

脚本的字段清单是硬编码的：漏一个字段，同步后服务端就没有它，策略退回类属性兜底
—— 行为上碰巧正确，界面上却看不到；而「碰巧正确」会在下次改默认值时立刻变成
「两处不一致」。所以用 **AST 从 `apply_params` 里真抽出读取的 key** 做比对，
而不是再抄一遍字段名（抄一遍等于把同一个错误写两份）。

三条断言：

1. 脚本字段清单 == `apply_params` 读取的 `(节, 字段)` 集合（两个方向都比，多一个少一个都失败）
2. 脚本字段清单 == `cfg/strategy.yaml` 配置节内的字段集合
3. 每个字段都有非空 `desc`

AST 解析踩到两个点，都写进注释了：
- `match_config: dict[str, Any] = params.get("match", {}) or {}` 是 **`AnnAssign`** 不是 `Assign`，
  只判 `Assign` 会整条漏掉；
- 赋值右侧是 `ast.BoolOp`（`X or Y`），不是 `ast.Call`，直接判 `isinstance(value, ast.Call)` 同样漏。

**断言有效性已验证**：临时从清单删掉 `match.trend_days_limit` 后重跑，两条断言分别报出

```
apply_params 读取但脚本字段清单缺失（服务端同步不到）: [('match', 'trend_days_limit')]
cfg/strategy.yaml[swing_trading_strategy] 与脚本字段清单分叉：仅 yaml 有 [('match', 'trend_days_limit')]，仅脚本有 []
```

定位精确到字段，随后已还原。

## 七、未覆盖 / 待确认

1. **服务端界面保存 `strategy_params` 的行为未验证**。本次通过 API 写入的是纯值结构
   （与读取到的一致）；如果界面在保存时改写成别的结构（例如加 `{desc, value}` 包装），
   脚本下次 diff 会显示为「值不同」，届时按实际结构调整脚本。
2. **值来源的边界（已修订）**：默认「补缺不覆盖」之后，`cfg/strategy.yaml` 只是
   **新字段的初始值来源**，不再是服务端的日常真源。要让某个用户策略用不同参数
   （例如「我的波段交易策略」用更低的 ADX 门槛），直接在服务端界面上改即可，脚本不会再
   把它冲回默认值。反过来，本端改了默认值想推到实盘，才需要 `--align-values`。
3. **同类问题存在于另外两个策略**。`strong_rebound`（模板 `6a5884d528893aa08c3e805b`）
   与 `volume_expansion`（模板 `6abb3227276f35f51ff8381c`）尚未核对用户策略侧的
   `strategy_params` 是否与模板/类属性一致。脚本已支持 `--scope user` 的框架，
   但字段清单需要先为这两个策略补上；本次未做，因为用户需求聚焦波段策略。

## 八、语义修订：默认「只补缺」，不「覆盖」

### 1. 问题

初版脚本把 `cfg/strategy.yaml` 当唯一真源，写入时用 yaml 值**全量覆盖**服务端两处。
这会冲掉服务端界面上的调参：yaml 值与类属性默认值由
`tests/strategy/test_param_defaults_consistency.py` 保证相等，所以「冲回 yaml 值」
实际就是「冲回代码默认值」，等于**界面调参无法持久化**。

本次写入没有造成损失，只因为两个用户策略的参数是本次新同步进去的、与默认值逐项相同
（见第六节）。但只要在界面上动过任何一个数，下次跑脚本就会抹掉它。

### 2. 根因：两类载体的语义不同

| 载体 | 语义 | 该不该被拉向本端值 |
| --- | --- | --- |
| 模板 `default_params` | 新用户策略继承的**默认值** | 该，默认值归代码管 |
| 用户策略 `strategy_params` | 用户自己的**定制值** | 不该，界面上调的 20 是刻意选择 |

初版对两类载体一视同仁地做全量覆盖，等于把「用户定制」当成「待纠正的默认值」。

### 3. 修订后的行为

新增 `_merge_params(current, target, overwrite)`，合并粒度是 `节.字段`：

| 模式 | 触发方式 | 服务端已有字段 | 服务端缺失字段 | 服务端独有字段（本端未定义） |
| --- | --- | --- | --- | --- |
| 补缺（默认） | 直接运行 | 保留现值 | 用本端值补入 | 保留，仅打印提示 |
| 拉齐 | `--align-values` | 用本端值覆盖 | 用本端值补入 | 保留，仅打印提示 |

「服务端独有字段」两种模式都保留：这类字段可能是已废弃参数，也可能是本端尚未纳入管理的参数，
脚本判断不了就不动。

返回值仍**全量**写回，不能只写差值：服务端 `PATCH` 对嵌套对象是赋值还是深合并没有承诺，
只传部分字段时若为赋值语义会把已有字段清掉。

回读校验（`_verify`）随之调整：校验「本端字段在服务端齐全」+「本次写入的字段值等于目标」，
不再要求「所有字段都等于本端值」。补缺语义下服务端保留界面调参，值不同是预期结果，不是失败。

### 4. 断言

`tests/test_sync_strategy_template_params.py::TestMergeParams` 五条：

1. 补缺模式保留服务端已调过的值，只补缺失字段
2. 拉齐模式覆盖同名键，服务端独有键仍保留
3. 服务端为空（`None` / `{}` / 某节为 `None`）时等价于全量写入
4. 模板 `{desc, value}` 包装的字段：已有字段连同 `desc` 一起保留
5. 不就地改写服务端响应对象（调用方还要用它做差异打印）

**断言有效性已验证**：把补缺分支临时改成无条件覆盖后重跑，两条断言失败，
报错信息直接指出后果：

```
AssertionError: 10 != 20 : 界面调参被冲回代码默认值
FAILED tests/test_sync_strategy_template_params.py::TestMergeParams::test_fill_missing_keeps_server_values
FAILED tests/test_sync_strategy_template_params.py::TestMergeParams::test_wrapped_template_keeps_existing_desc_and_value
```

随后已还原（源码中 `if field in bucket and not overwrite:` 恢复）。

### 2. 守卫改造

原守卫只测 swing（硬编码 `STRATEGY_FIELDS["swing"]` 与策略类名）。改为遍历三张注册表，

`STRATEGY_SOURCES` 的键集合必须一致，且每个条目必须有 `label` / `yaml_section` / `template_id`。

新增策略时最容易只改一处（例如只加 `STRATEGY_META` 就以为完事），那种情况下守卫会
**静默不覆盖**该策略，跑起来一切正常。

`_extract_param_keys` 同时去掉 `class_name` 参数，改为「找含 `apply_params` 的那个类」，
策略类改名不再让守卫失效。

### 4. 一个实证：`反弹交易策略` 的 `buy.min_score` 是 4.0，不是 6.0

dry-run 输出：

```
buy.min_score                  4.0              6.0              值不同
用户策略 '反弹交易策略' 无待写入字段，未写入（已有值按补缺语义保留）
```

模板与 `cfg/strategy.yaml` 都是 `6.0`，而这个用户策略上是 `4.0`。若按初版的「全量覆盖」

买入信号会明显减少。这是一次真实的、会影响交易行为的改动，而它在覆盖语义下不会有任何提示。

第八节的修订正是为了避免这类改动，本例是它第一个真实受益点。若确实要把它拉齐到 6.0：

