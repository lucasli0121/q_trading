# 执行记录取数失败时从订单流水重建持仓

日期：2026-09-24
范围：`q_trading_work/trade/manager.py` 与对应测试
决策来源：用户确认「① 从订单流水重建持仓；② 订单流水也失败则放弃本次新记录」

## 一、问题

`TradeManager._update_strategy_execution()` 每次成交都会读服务端最近一条执行记录
（`GET /api/user_strategy/execution/latest`），在其基础上计算持仓与资金并新增一条记录：

```python
try:
    exec_data = self._user_strategy_api.get_latest_execution(user_strategy_id)
except Exception:
    self.logger.warning("加载最近执行记录失败，本次执行记录将以零持仓为基础重建")

execution = StrategyExecutionDao(user_strategy_id=user_strategy_id)   # 零持仓
if exec_data:
    execution.from_db(exec_data)
```

取数失败时 `exec_data` 为空，记录以**零持仓**为基础重建，已有持仓从新记录里消失，
只剩本次成交的那只。之后工作流每次读到的持仓都是残缺的：卖出信号会被判成「无持仓，跳过卖出」，
资金口径里的持仓成本也同步失真。

## 二、改动后的分支

`_update_strategy_execution()` 现在按三种情况处理：

| 情形 | 处理 | 日志 |
| --- | --- | --- |
| 读到执行记录 | 原逻辑：`from_db` 后应用本次成交 | 无 |
| 取数失败（超时/5xx/连接） | **从订单流水重放持仓**；流水也失败 → 放弃本次记录 | 失败 WARNING，重建成功 INFO，两者皆失败 ERROR |
| 无执行记录（404 收敛为 `{}`） | 也尝试从流水重建；流水失败 → 按零持仓继续（`{}` 是合法初始状态，不放弃记录） | 流水失败 WARNING |

「放弃本次新记录」的语义：不写这条执行记录，直接返回。订单本身已落库，
下一次写入成功时会从订单流水重建出完整持仓，记录自愈。

放弃时的 ERROR 日志带本次成交要素，便于人工对账：

```
持仓与订单流水均取不到，放弃本次执行记录（订单已成交并落库，下次成功写入时从订单流水重建）
user_strategy_id=6aab518a…, code=600000, action=买入, qty=100, price=11.2000
```

## 三、重建实现

新增 `TradeManager._rebuild_execution_from_orders(user_strategy_id, exclude_order)`：

1. `GET /api/order/list/{user_strategy_id}` 取订单流水（服务端该接口无分页，返回该策略全部订单）。
2. 只重放成交订单：`status == 成功`（`execute_order` 落库时写死该状态，并以 `entrust_quantity`
   回填 `trade_quantity`），且 `trade_quantity > 0`，且 `action ∈ {买入, 卖出}`。
   撤单、失败、零成交量记录不参与。
3. 按 `create_time` 升序重放，**逐条调用既有的 `_apply_order_to_positions`**。
   成本价含买入手续费、加仓加权、卖出减仓与清仓等规则与实时链路完全共用，不存在第二套口径。
4. `current_profit` = 各卖出订单 `profit_amount` 累加，与 `_refresh_execution_metrics`
   的「已实现收益累计」同口径。
5. `start_date` = 最早一笔买入订单的日期，使 `execution_days` 与年化收益率可正常回算。

### 排除本次成交订单

`_execute_and_notify` 的顺序是先保存订单、再更新执行记录，因此重建时本次订单**已经在流水里**。
若不排除，本次持仓与已实现盈亏会被计入两次（重建一次、下游 `_apply_order_to_positions` 再一次）。
重建按 `id` 排除本次订单，订单没有 id 时退回按 `client_order_id` 匹配。

### 局限

- 重建出的 `t1_qty` / `t1_day` 是重放后的值，可能与最后交易日的真实可卖量有偏差。
  T+1 只影响卖出数量的收敛，不影响持仓与资金口径。
- 重建耗时与订单笔数线性相关，且每只新出现的持仓会查一次股票名称（已有缓存）。
  重建只在取数失败或无执行记录的路径触发，不在每次成交的常规路径上。
- 放弃记录后，服务端持仓视图会滞后本次成交，直到下一次成功写入。这是用户选定
  「宁可不写残缺记录」的代价；`log/pending_execution.jsonl` 补偿队列只覆盖
  「记录已构造好但保存失败」，此处没有可补投的 payload，故不入队。

## 四、测试

`tests/test_trade_manager.py` 新增 5 条，并把两个测试类的 `_manager()` 工厂统一注入
`_order_api` 桩（`list` 默认返回空列表），避免用例真的发 HTTP：

| 用例 | 覆盖点 |
| --- | --- |
| `test_rebuild_positions_from_orders_on_load_failure` | 重建出 2 只持仓；本次订单只计入一次（300 股而非 400）；撤单记录不参与；`start_date` 取最早买入日 |
| `test_rebuild_accumulates_realized_profit_from_orders` | `current_profit` = 历史卖出 `profit_amount` 累计（200） |
| `test_give_up_execution_record_when_both_sources_fail` | 两个来源都失败：`save_execution` 未被调用，留 ERROR |
| `test_no_execution_record_and_order_flow_failure_keeps_writing` | 无执行记录 + 流水失败：仍按零持仓写入，留 WARNING |
| `test_update_strategy_execution_api_error` | 原用例保留，断言改为「已改走订单流水重建」 |

回归结果（容器内执行，分两段）：

```
tests/（排除 tests/strategy、hangle_bar）   305 passed, 1 skipped
tests/strategy + hangle_bar                  60 passed, 1 skipped
```

合计 366 passed、0 failed。

守卫敏感性反证：临时把 `exclude_order=order` 改成 `exclude_order=None` 后，
`test_rebuild_positions_from_orders_on_load_failure` 立刻失败（持仓变成 400 股），
其余两条通过（不涉及重复计入），随后还原并复跑通过。这说明「排除本次订单」这条
关键逻辑确实被测试锁住。
