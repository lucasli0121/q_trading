# 日志 DEBUG 放行范围收窄报告

日期：2026-10-09
改动文件：`cfg/log.yaml`、`tests/test_log_config.py`、本报告
状态：已改完，重新打包部署后生效

## 一、问题

上一轮把 DEBUG 打开后，`info.log` 确实出现了业务 DEBUG（`配置对账完成…无变更`），
但同时被第三方库刷屏：

```
2026-10-09 11:02:35,036-httpcore.http11-47-DEBUG: send_request_headers.started request=<Request [b'GET']>
2026-10-09 11:02:35,037-httpcore.http11-47-DEBUG: send_request_body.complete
2026-10-09 11:02:35,063-httpcore.http11-47-DEBUG: receive_response_headers.complete return_value=(b'HTTP/1.1', 200, b'OK', ...)
2026-10-09 11:03:34,739-api.client-295-DEBUG: GET /api/strategy/list params=None
2026-10-09 11:03:34,737-apscheduler.scheduler-1153-DEBUG: Looking for jobs to run
```

## 二、判断依据

`httpcore.http11`、`apscheduler.scheduler`、`api.client` **都没有被 `cfg/log.yaml`
显式配置过**，它们的 effective level 只能逐级向上继承到 `root`。它们能打 DEBUG，
只有一个解释：**生成机器上那份配置的 `root.level` 是 `DEBUG`。**

`workflow.strategy_workflow` 打 DEBUG 是上一轮的设计（`loggers.workflow`），
这部分是对的；问题出在 root 被一起抬高了。

顺带核对：日志里的行号与仓库源码完全一致（`配置对账完成` = strategy_workflow 第
1208 行、`尚无执行记录` = 第 577 行、`GET %s params=%s` = api/client 第 295 行），
说明生成机器上跑的构建是当前代码，不是陈旧产物。

## 三、量化（只读探针，稳态一轮对账）

稳态 = 对账启动后无变更的那一轮（首轮会把 5 条策略全部 added，请求数远多于稳态）。
统计口径只取 `info_file_handler` 写出的行 —— 生产上 console 去 stdout、
error_file_handler 只收 ERROR，只有它落 `info.log`（把多个 handler 写进同一缓冲
会把「冒泡到多个 handler」的记录重复计数）。

| 场景 | 配置 | 本轮行数 | 其中 DEBUG | 一天（240 轮） |
|---|---|---|---|---|
| A | `root=INFO` + `loggers.workflow=DEBUG` | 13 | 1 | 约 3 100 |
| B | `root=DEBUG`（你贴的日志对应的配置） | **144** | 132 | 约 34 600 |
| C | `root=DEBUG` + 钉住 httpcore/urllib3/pymongo | 24 | 12 | 约 5 800 |
| D | 交付的 `cfg/log.yaml` 原样 | 13 | 1 | 约 3 100 |

B 比 A 多 11.1 倍，多出来的 132 行里 **120 行是 `httpcore.http11`**。稳态一轮对账
只发 12 次 HTTP，即**每个请求约 10 行报文级细节**（`send_request_headers.started`
这种），对排查业务问题没有价值。

## 四、改法

`cfg/log.yaml` 三处：

**1. `root` 保持 `INFO`** —— 这是关键。业务 DEBUG 靠 `loggers.workflow` 单独放行，
不要动 root。

**2. 保留 `loggers.workflow`（DEBUG + `propagate: false`）** —— 与上一轮一致。
`propagate: false` 不能去掉，否则记录冒泡到 root 的 handlers 会输出两遍；
`handlers` 必须列全三个，`propagate: false` 之后不再借用 root 的 handler 列表，
少列 `error_file_handler` 的话 ERROR 就进不了 `errors.log`。

**3. 新增第三方库降噪段（防御性）**：

```yaml
  httpcore:
    level: WARNING
  urllib3:
    level: WARNING
  pymongo:
    level: WARNING
```

`root=INFO` 时这三条是冗余的，留着是为了**防止以后有人把 root 临时调成 DEBUG 时
被刷屏** —— 实测能把 144 行/轮压到 24 行/轮。

`httpx` 与 `apscheduler` 故意不在此列：httpx 每个请求一条 INFO
（`HTTP Request: GET … "HTTP/1.1 200 OK"`）是有用的请求流水；apscheduler 的
`Running job` / `executed successfully` 是判断对账有没有在跑的主要依据。

## 五、验证

**放行范围**（对交付配置实际 `dictConfig` 后逐个查 `getEffectiveLevel`）：

| logger | effective | DEBUG 放行 |
|---|---|---|
| `workflow.strategy_workflow` | DEBUG | 是 |
| `workflow.base_workflow` | DEBUG | 是 |
| `api.client` | INFO | 否 |
| `httpx` | INFO | 否 |
| `httpcore` / `httpcore.http11` | WARNING | 否 |
| `urllib3` / `pymongo` | WARNING | 否 |
| `apscheduler.scheduler` | INFO | 否 |
| `core.tools` / `trade.notifier` | INFO | 否 |

**探针四场景**：交付配置（D）的实测行数与 A 完全一致（13 行/轮），
说明它恢复到了「只放行业务包」的本意。

**新增守卫测试** `tests/test_log_config.py`（7 项）：root 必须是 INFO、
workflow 必须 DEBUG 且 `propagate=false`、workflow 的 handlers 必须含
`error_file_handler`、info handler 不能把闸门设在 INFO、噪音库必须钉 WARNING、
httpx/apscheduler 不能被静音、每个 handler 都要被引用。

**突变验证**：把 `root.level` 改成 `DEBUG` 重跑，`test_root_level_stays_info`
立刻失败（1 failed, 6 passed），还原后 7 passed —— 守卫确实能抓住这次的问题改法。

**回归**：全量 604 passed, 2 skipped。

## 六、部署

生成机器跑的是打包产物，配置在 `_internal/cfg/log.yaml`（与源码 `cfg/log.yaml`
是两份文件）。两条路：

- 直接改生成机器上的 `_internal/cfg/log.yaml`：把 `root.level` 改回 `INFO`，
  加上 `loggers.workflow` 与三条降噪 pin；
- 或者重新打包，用源码里的这份覆盖。

改完重启进程。之后每轮对账在 `info.log` 里应只多一行
`配置对账完成（reason=scheduler）: 无变更`，加 12 行 httpx 请求流水。

若确实需要更细的 HTTP 请求日志，放行 `api` 包（每个请求一行，比 httpcore 干净），
配置注释里给了现成片段。
