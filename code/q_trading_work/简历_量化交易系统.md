## 三、核心职责与成果（简历正文，建议保留 4–6 条）

1. **设计并实现四服务分层的量化系统架构**：数据采集、数据服务、策略执行三者职责隔离，
   统一通过 `AppContext` 单例管理全局服务、DAO 层封装数据序列化、API 层封装 HTTP 客户端
   （token 鉴权 + 重试 + 错误分类）。服务间通过 MQTT 订阅配置变更，实现**配置热更新**——
   服务端写库后推送通知，执行引擎 60 秒内热生效，无需重启。

2. **实现因子与策略框架**：基于注册表模式设计 `FactorManager`，抽象 `BaseFactor`
   统一因子契约；落地 **16 个技术因子**（趋势、支撑阻力、量价、回撤等族），
   基于 ta-lib 计算并做 NumPy 适配；实现 **4 套策略**（强势反弹、波段网格、成交量放大等），
   统一 `is_match_strategy` 选股 + 分钟/实时双通道买卖判定 + `before_trading` 盘前钩子。

3. **实现回测引擎并建立「数据完整性 fail-closed」准则**：滑窗遍历历史日 K 调用策略选股逻辑，
   模拟次日开盘买入 / N 日后卖出，产出收益与回撤统计并持久化到服务端。
   **取数失败时中止回测且不写库**，严格区分「取数失败」与「正常无信号」，
   修复了同一份配置跑出 2/0/4/3/0 笔不可复现结果的问题。

4. **建立 627 项自动化测试的可回归体系**：覆盖因子计算、策略信号、回测、交易成本、
   API 契约、配置对账、日志配置等。为难以复现的缺陷沉淀**突变验证**习惯
   （改回缺陷代码必须让守卫测试失败），并输出 28 份缺陷分析与修复报告。

5. **完成打包交付与多实例部署**：用 PyInstaller 打包为 onedir 产物交付到生产机，
   处理配置路径、运行时钩子、日志文件等打包态差异；针对第三方数据源免费额度限制，
   设计**多实例分片采集**方案（多账号按股票代码互斥分片，MQTT client_id 拼接实例名避免
   容器内 PID 冲突），并用分片体检脚本验证覆盖度与均衡性。

6. **排查并修复多个线上静默故障**（详见第四节），典型问题是「功能失效但日志全绿」。

## 四、可展开的技术亮点（面试用，按需取一条展开讲）

### 亮点 1：MQTT 池级订阅空转 —— 一个集合承担两种语义
**现象**：推送端 topic / payload 全部正常，本端一条行情都收不到；日志里只有一条
`MQTT 订阅 topic 成功: q_share/config_change (mid=1)`，没有任何池级订阅记录，
但订阅函数返回 `True`、零错误日志。

**根因**：`_subscribed_pool_ids` 一个集合同时表示两种语义——
「打算订阅哪些池」与「已经订阅哪些池」。启动初始化把意图预填进集合，
而订阅方法用「在集合里」判断「已订阅」并短路返回，导致订阅循环整个空转：
登记 4 个池、broker 侧 0 个订阅。

**修法**：意图与事实分离。新增钩子 `_collect_startup_pool_ids()` 提供意图，
`_subscribed_pool_ids` 只由真正订阅成功的一方写入（订阅失败回滚登记）。
新增 8 项守卫测试，断言「登记表里的每个池都必须有真实订阅记录」。
**命名约定固化为规范**：`_subscribed_*` = 事实，`_collect_startup_*` = 意图，两者不共用集合。

### 亮点 2：定时任务「每两轮跳一轮」—— 节流阈值等于调度周期
**现象**：调度器日志里任务执行耗时严格交替（365ms / 1ms / 335ms / 0ms），
两轮都报执行的 1ms 那轮实际什么都没做。

**根因**：节流阈值恰好等于轮询周期（都是 60 秒），且时间戳记在对账**结束**时刻，
于是每两轮必然跳过一轮，实际周期变成 120 秒（非交易时段 600 秒）。

**修法**：阈值乘 0.9 留出余量（54 / 270 秒），跳过分支补 INFO 日志。
用探针模拟 8 轮调度验证：修复前只跑 4 轮，修复后 8 轮全跑。

### 亮点 3：日志「两道闸门」—— 改了配置却看不到 DEBUG
**现象**：把文件 handler 的级别改成 DEBUG，日志里依然一条 DEBUG 都没有。

**根因**：Python logging 有两道独立闸门——`logger.isEnabledFor()`（由 logger 及祖先的
effective level 决定）与 `handler.level`。只改第二道无效，因为记录在第一道就被
root=INFO 拦掉，`LogRecord` 根本没被创建。

**修法**：给业务 logger 单独开 `level: DEBUG` + `propagate: false`（避免冒泡到 root 重复输出，
并自带 error handler 保证 ERROR 仍进错误日志）。随后又遇到**另一个方向的问题**——
为看 DEBUG 把 root 抬到 DEBUG 后，`httpcore` 等第三方库的报文细节刷屏。
用探针量化三种配置的日志体积（每轮 13 行 / 144 行 / 24 行），
最终方案是 root 保持 INFO + 对噪音库钉 WARNING，并用 7 项配置守卫测试固化。
**方法论**：先量化再决定收窄范围，不靠感觉调级别。

### 亮点 4：覆盖全部档位的因子可达性验证
**问题**：区间类因子的打分档位（如布林带轨道 ±1σ / ±2σ）在真实数据上可能**永远取不到**
——因为轨道窗口包含当根价格，单根触及 `m·σ` 的必要条件是 `m ≤ √n`，
参数设成 3σ 时档位恒死，表现为「这个因子永远给不出高分」。

**做法**：不靠读代码下结论，构造函数化数据**逐档扫一遍**，确认每一档都可达；
并把方法固化成可复用的测试模板（`elif` 链 + 区间比较必须构造数据逐档验证）。
同类问题还查出：支撑阻力因子的某个档位被前置条件包含而恒死、
talib ADX 因 lookback = 2×period 导致数据不足时返回 NaN 并被判成反向负分。

### 亮点 5：多数据源分级回退与采集容量规划
**设计**：`StockFetch` 作为中心编排器，按「Redis 缓存 → 免费源(akshare) → 付费源(TickFlow)」
顺序回退，成功结果写回 Redis；用 APScheduler 按交易日历（`exchange_calendars` 上证日历）
只在 9:00–15:00 调度，区分实时行情 / 日 K / 财务数据的不同同步周期。

**容量规划**：第三方免费套餐单账号采样上限 45 标的/分钟，而股票池约 109 只。
推导出容量公式 `单实例上限 = (每分钟请求数 × 单次标的数 × 同步间隔) / 2`，
落地方案是 3 个实例按股票代码互斥分片，并写体检脚本验证「分片互不重叠」与
「单实例不超过上限」这两个必要条件。

## 六、使用的表述注意

- 项目定位写「**辅助决策工具**」而不是「自动交易系统」——系统不自动下单，
  信号由人工决策后执行，这是设计意图不是功能缺失。
- 「四件套 + 小程序」的模块划分、代码行数、测试数量均可在仓库复核。
- 若面试追问策略收益，注意**回测结论必须带数据快照时点**：
  同一份配置因服务端日 K 数据持续增长，结论会随时间变化
  （实测同一命令由 18 笔 +11.32% → 28 笔 +5.52% → 39 笔 −9.16%）。
  这是数据的特性，谈的时候要主动说明，不要拿单次数字当结论。
