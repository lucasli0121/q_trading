## 一、需求一：盘后个股阀门

### 1.1 口径（AskUserQuestion 两轮确认）

| 问题 | 选定口径 |
| --- | --- |
| 作用维度 / 存放位置 | 按**股票**维度，落**服务端新表** |
| 触发判据（买入） | 当日支撑位跌破 ≥2 次；**二次修订**：按 **S1/S2/S3 中最深被破的档**定幅度 |
| 卖出侧 | **对称**：卖出后站上 R 阻力档 ≥2 次（卖飞）→ 次日卖出门槛上调 |
| 生效范围 | 只对**该股、次日、同侧**生效 |

一句话语义：**信号之后出现不利走势 → 抬高该侧门槛。**

### 1.2 计算与生效链路

```
当日 15:10（[scheduler] after_trading_hour/minute）
  workflow.daily_after_trading()
    → 查当日交易信号（按 user_strategy_id + 当日时间段）
    → 按股票聚合买卖信号时间
    → BaseStrategy.compute_daily_valve(code, date, buy_times, sell_times)
         S1/R1 取「上一交易日日线」的经典枢轴点（InDaySRFactor.pivot_points，与 swing 盘中同源）
         strategy/valve.py::compute_stock_valve 统计穿破分钟数
    → StrategyDailyValveApi.add() 写入服务端 strategy_daily_valve_tbl

次日盘前（_run_daily_selection_for_state 内、before_trading 之后）
  workflow._apply_daily_gates(state, trade_date)
    → _resolve_market_offset(trade_date)      # 涨跌停偏移，按日缓存一次（见第二节）
    → StrategyDailyValveApi.list(usid, trade_date=前一交易日)  # 精确查前一交易日
    → instance.set_daily_valves(...) / clear_daily_valves()
```

关键点：

- **按「前一交易日」精确查询**，不取最新一条。源交易日没有记录就说明当天没算，不该沿用更早的。
- **阀门每日重算、不累积**。`compute_stock_valve` 触发时返回 `min(VALVE_STEP × 档位序号, VALVE_MAX)`，
  未触发为 `0`，因此单侧实际取值是 **{0, 1.0, 2.0, 3.0}** 四档之一（10 分制）。
  「每日的阀门值可能不一样」由「当天破到哪一档」决定，不是逐日累加。
- **fail-open**：读阀门表失败、支撑/阻力位取不到、分钟数据不足，一律偏移 0（不限制）。阀门是附加收紧项，缺失不应改变原有行为。
- 触发但穿破次数为 0 的股票不写库；当日无信号直接跳过。

### 1.4 多档支撑/阻力（二次修订）

`InDaySRFactor.pivot_points()` 本来就给出 `s1/s2/s3/r1/r2/r3` 六档（昨日振幅的 1/3、2/3、1 倍），
原先只取了 `s1/r1` 两档，等于把「跌破得有多深」这个信息丢掉了。

现改为**按触达的最深档给倍数**：

| 触发情况（锚点=当日最早同向信号之后） | 次日买入/卖出门槛上调 |
| --- | --- |
| 跌破 S1 ≥2 分钟 | +1.0（= 1 × `VALVE_STEP`） |
| 跌破 S2 ≥2 分钟 | +2.0 |
| 跌破 S3 ≥2 分钟 | +3.0 |
| 未达 2 分钟 | 0 |

三条设计约束：

1. **档位不叠加**。价格单调下行时，「跌破 S3」的那些分钟必然同时满足 `< S1` 与 `< S2`，
   逐档相加等于把同一分钟数重复计三次。实现上取「最后一个满足阈值的档」即可。
2. **每档要各自达标**。S3 只被穿 1 次（不到 `VALVE_MIN_BREAKS=2`）时按次深档 S2 算，不能直接给最高档。
3. **S3 命中是有意义的信号**。三档是昨日振幅 `D` 的 1/3、2/3、1 倍，价格落在昨日区间内时
   `|price − pivot| ≤ 2D/3`，所以**触及 S3/R3 必然意味着突破昨日低点/高点** —— 这是「创昨日新低」，
   给最高档有依据，不是拍脑袋。

入库仍只用 `buy_valve` / `sell_valve` 两个数值（服务端字段不变），但 `reason` 里带上各档明细，
例如 `买入后破位 S1/S2/S3=30/12/3次(阈值2，最深S3 ⇒ 买入门槛+3.0)`，便于事后反查谁把门槛抬起来的。

### 1.3 门槛偏移的统一口径（三策略共用）

`BaseStrategy` 新增两个方法，**正 = 更难**：

```
buy_threshold_offset(code)  = 个股买入阀门{0/1.0/2.0/3.0} + 市场买入偏移{0/0.5/1.0/2.0/3.0}
                              + 趋势向下项{0/1.0}                          ← 三次修订
sell_threshold_offset(code) = 个股卖出阀门{0/1.0/2.0/3.0} + 市场卖出偏移{0/−0.5/−1.0/−1.5}
                              + 趋势向上项{0/1.0}                          ← 三次修订
```

三项都是**收紧**方向，互相独立；`VALVE_ENABLED=False` 只关个股阀门项，
`TREND_GATE_ENABLED=False` 只关趋势项，市场项不受任何一个开关影响。

极端利空禁买（§2.3）**不走这条偏移链**，而是在买入判定入口直接返回不成立 ——
否则会出现「门槛抬到 11 分（满分 10），靠不可达来间接实现禁买」这种依赖巧合的写法。

6 处接入点：

| 策略 | 侧 | 原判定 | 现判定 |
| --- | --- | --- | --- |
| 波段 swing | 买 | `avg_score > 0` | `avg_score > buy_offset` |
| 波段 swing | 卖 | `final_score < 0` | `final_score < -sell_offset` |
| 成交量 volume | 买 | `combined >= MIN_SCORE` | `>= MIN_SCORE + buy_offset` |
| 成交量 volume | 卖 | `score <= SELL_MAX_SCORE` | `<= SELL_MAX_SCORE - sell_offset` |
| 强趋势 strong | 买 | `avg_score >= BUY_MIN_SCORE` | `>= BUY_MIN_SCORE + buy_offset` |
| 强趋势 strong | 卖 | `score < SELL_MAX_SCORE` | `< SELL_MAX_SCORE - sell_offset` |

触发时 reason 文案追加「买入门槛偏移+x.xx / 卖出门槛偏移+x.xx」，便于从信号明细反查是谁抬高了门槛。

## 二、需求二：涨跌停家数 → 全局门槛偏移

### 2.1 分档表（按实测行情重新标定，二次修订）

以**前一交易日**全市场跌停家数为市场风险代理。

**基数从实测来**（`akshare` 涨跌停池，能取到的全部 16 个交易日，2026-09-14 ~ 10-13）：

| 日期 | 跌停 | | 日期 | 跌停 |
| --- | --- | --- | --- | --- |
| 09-14 | 16 | | 09-23 | 13 |
| 09-15 | 27 | | 09-24 | 13 |
| 09-16 | 4 | | 09-28 | **56** |
| 09-17 | 1 | | 09-29 | 10 |
| 09-18 | 0 | | 09-30 | 9 |
| 09-21 | 2 | | 10-08 | 13 |
| 09-22 | 3 | | 10-09 | 8 |
| | | | 10-12 | 19 |
| | | | 10-13 | 8 |

**中位 10、75 分位 16、90 分位 27、最大 56。** 全序列 `0,1,2,3,4,8,8,9,10,13,13,13,16,19,27,56`。

按「>20 已经很利空」定分界，`utils/market_breadth.py::DEFAULT_BANDS` 改为：

| 跌停家数 | 买入门槛 | 卖出门槛 | 实测命中天数 |
| --- | --- | --- | --- |
| ≤5 | +0.0 | −0.0 | 5 天（0/1/2/3/4） |
| 6 ~ 10 | +0.5 | −0.5 | 4 天（8/8/9/10） |
| 11 ~ 20 | +1.0 | −1.0 | 5 天（13/13/13/16/19） |
| 21 ~ 30 | +2.0 | −1.5 | 1 天（27） |
| >30 | +3.0 | −1.5 | 1 天（56） |

方向：跌停越多 = 市场越弱 = **更难买、更容易卖**（风控优先）。

**卖出侧单独设上限 `max_sell_offset`（默认 1.5）**。卖出侧取负号 = 放宽卖出门槛，
幅度过大（例如 −3.0 分）意味着「任何轻微负分都卖」，会把正常持有打成高频进出，
而本项目实测「交易越密、亏损越重」。故只做「提前止损」，不做「无脑清仓」。

**超出最后一档按最后一档取值**，不回落 0 —— 跌停家数只会向「更差」方向超出，
回落 0 等于在最需要收紧的那天把机制关掉。也正因为这个兜底，配置里不必写 `inf`。

分档与上限都可配置（`cfg/stock.cfg`，部署机上改完重启即可，不必重新打包）：

```ini
[market_breadth]
bands = 5:0,10:0.5,20:1,30:2,9999:3
max_sell_offset = 1.5
```

配置缺失 / 格式非法 / 上界非升序 → 回退到代码里的 `DEFAULT_BANDS` 并打 WARNING（不会静默变成「不限制」）。

取不到数据、`None`、负数 → 0.0（不限制）+ WARNING。按「拦全部」兜底会让一次接口抖动停掉整个实例的买卖。

结果落 `market_breadth_daily_tbl`（唯一键 `trade_date`），可用 `GET /api/market_breadth/list` 回看每日家数与偏移。

**对门槛的实际影响**：三策略买入基准分别是 6.0（强趋势）/ >0（波段）/ 5.0（成交量）。
最坏情况（市场 +3.0 且个股破 S3 +3.0）合计 +6.0，会把强趋势的门槛抬到 12.0、成交量抬到 11.0 ——
**均超过 10 分满分，等于当天不开新仓**。这发生在「跌停 >30 家 + 该股当日破 S3」的极端组合，
符合「极端利空不做」的意图；若希望保留少量交易，调小 `bands` 最后一档或 `max_sell_offset` 即可。

### 2.2 数据源限制（必须记住）

akshare 涨跌停池接口 **只有最近约 30 个交易日**：`stock_zt_pool_dtgc_em` 更早日期直接抛错，
`stock_zt_pool_em` 更早日期返回 0。因此：

- 本机制 **实盘盘前可用**（拉前一交易日）；
- **历史回测无法验证**（本次回测窗口 2026-07-21 起，早于数据边界）；
- 部署机需装 akshare 且能访问外网，否则偏移恒为 0。

### 2.3 极端利空禁买（三次修订）

**两个条件同时成立**才触发，缺一不可：

1. 前一交易日跌停家数 **严格大于** `[market_breadth] stop_buy_limit_down`（默认 30）；
2. 该股盘后阀门达到 `VALVE_STOP_TIER` 档 —— 即当日买入侧**跌破 S3**（触发值 3.0）。

触发后果是**硬性**的：该股当日 `_check_buy_conditions` 直接判不成立（`is_buy_blocked`），
不受 `buy_threshold_offset` 影响；**卖出与风控判定完全不受影响**（「只卖不买」）。

为什么是交集而不是并集：

- 只看市场（跌停多但个股没破位）—— 门槛已被市场偏移抬过，没必要一封到底；
- 只看个股（破 S3 但市场不极端）—— 只抬门槛、仍留极强信号的机会；
- 两者的交集才是「极端利空 + 个股破位」这个真正的停手条件。

三道 fail-open（任一条成立就不禁买）：跌停家数取不到（`None`）、`stop_buy_limit_down <= 0`、
`VALVE_STOP_TIER × VALVE_STEP <= 0`。理由与市场偏移一致 —— 一次接口抖动不该停掉整个实例的买入。

实现：`StrategyWorkflow._apply_buy_block`（盘前，紧跟阀门注入）+ `BaseStrategy.set_buy_blocked`
/ `is_buy_blocked`（三策略买入入口统一查）。名单**整体替换**，不跨日累积。

### 2.4 日线趋势门槛（三次修订）

原 swing 的「日线趋势向下 ⇒ 当天跳过买入判定」是**硬闸门**（2026-09-29 引入）。
按用户要求改成**门槛**，并在成交量策略上加同一套：

| 趋势方向 | 判定（ADX 口径） | 后果 |
| --- | --- | --- |
| 向下 | `ADX >= 25` 且 `-DI > +DI` | 买入门槛 +`TREND_BUY_OFFSET`（默认 +1.0） |
| 向上 | `ADX >= 25` 且 `+DI > -DI` | 卖出门槛 +`TREND_SELL_OFFSET`（默认 +1.0） |
| 判不出 | ADX 不足 / NaN | 不偏移 |

**为什么改成门槛后必须同时去掉「选股阶段剔除」**：swing 的 `is_match_strategy`
原先在选股条件 0 就把趋势向下的股票剔掉了。如果保留剔除，门槛永远拿不到这些股票
（选股阶段就被挡住），等于「改成门槛」退化成原来的硬闸门。因此：
选股条件 0 改为一律不剔除、只把方向记进集合；盘中 `handle_minute_bar` 去掉
`if not downtrend and not break_max` 这段短路，让 `_check_buy_conditions` 的门槛去管。

**为什么成交量策略的趋势判定放在 `before_trading`**：判定要取日K（HTTP），
而 `_check_buy_conditions` 在分钟级被高频调用，盘中打 HTTP 会拖慢甚至阻塞交易线程。
盘前一次性取完（基类 `load_daily_trend`），盘中只查集合。

判定口径与 swing 共用基类 `_daily_trend_direction`，ADX 是 NaN 时一律判不出
（次新股、停牌复牌不偏移）。

## 四、需求三：三策略 × 三池对比回测

窗口 `2026-07-21 09:30:00` ~ `2026-10-13 15:00:00`，分钟频，初始资金 10 万，
默认口径（风暴过滤关、成交间隔 0、资金不分片），持有 5 日，信号窗口 40。

| 策略 | 股票池 | 笔数 | 胜率 | 总收益 | 最大回撤 | 平均单笔 |
| --- | --- | --- | --- | --- | --- | --- |
| 强趋势(反弹) | 实际持仓(7) | 25 | 12.00% | −29.06% | 29.06% | −2.31% |
| 强趋势(反弹) | 自选股(19) | 26 | 7.69% | −30.10% | 30.10% | −2.31% |
| 强趋势(反弹) | 科技池(22) | 330 | 10.91% | −81.05% | 81.05% | −1.15% |
| 波段 | 实际持仓(7) | 581 | 13.86% | −92.84% | 92.84% | −0.92% |
| 波段 | 自选股(19) | 735 | 9.28% | −96.89% | 96.89% | −1.15% |
| 波段 | 科技池(22) | 1024 | 19.17% | −94.63% | 94.63% | −1.20% |
| 成交量 | 实际持仓(7) | 256 | 9.88% | −71.47% | 71.62% | −0.82% |
| 成交量 | 自选股(19) | 328 | 6.13% | −86.68% | 86.75% | −1.11% |
| 成交量 | 科技池(22) | 1327 | 11.23% | −98.81% | 98.81% | −1.04% |

**9 组全部为负。** 三条规律：

1. **池越大、交易越密、亏得越重**。同一策略从 7 只扩到 22 只，笔数涨 4~5 倍，总收益再降 20~60 个百分点。
2. **胜率低的策略亏得更多，但胜率高的也没救**。波段在科技池胜率 19.17%（三者最高）仍是 −94.63%；
   平均单笔 −1.20% × 1000 笔，靠胜率翻不过来。
3. **平均单笔全部落在 −0.8% ~ −2.3%**。和此前 000988 单票测试的「每笔往返成本约 0.5%」对照，
   信号的毛贡献接近 0，扣成本后为负。

对照组：科技池（22 只）上三个策略各跑一遍「**资金分片 + 30 分钟成交间隔**」：

| 策略 | 基线：笔数 / 总收益 | 分片+30min：笔数 / 总收益 / 胜率 / 回撤 |
| --- | --- | --- |
| 强趋势(反弹) | 330 / −81.05% | 104 / **−8.64%** / 16.35% / 8.64% |
| 波段 | 1024 / −94.63% | 390 / **−13.47%** / 30.41% / 13.73% |
| 成交量 | 1327 / −98.81% | 133 / **−11.98%** / 17.29% / 12.00% |

三个策略方向一致：把交易笔数压到原来的 1/4 ~ 1/10，亏损从 −81% ~ −99% 收敛到 −9% ~ −13%，
回撤同步收敛。**但仍然全部为负**，说明降频与分片解决的是「过度交易放大亏损」，
没有把策略本身做成正期望。

需要说明的是，这一组**同时动了两个开关**（`split_capital_by_code=true` 与 `min_trade_interval_minutes=30`），
不能归因到其中任何一个；拆分归因需再补两组单开关回测。

另一点：**日频/分钟频回测都不走策略的卖出条件**（回测靠 `hold_days` 平仓），
本轮新增的阀门与涨跌停门槛**尚未接入回测链路**，上表是「未加门槛」的基线。
要在回测里验证阀门，需要在回测引擎里按日复算阀门并注入策略实例，属下一步。

## 六、已知边界与后续

1. **回测链路未接入**阀门、涨跌停门槛、极端利空禁买、日线趋势门槛（见第四节末）。
   回测里验证需在引擎内按日复算 —— 这四项**全部只在实盘链路（workflow）生效**。
2. **分档是主观标定**。本次依据的样本只有 16 个交易日（akshare 可得上限），
   「>20 很利空」这个分界来自用户判断而非统计。样本扩大后应重新标定，
   改 `cfg/stock.cfg [market_breadth] bands` 即可，不必改代码。
3. **涨跌停数据只有 30 个交易日**，历史不可回溯；实盘还需确认部署机装了 akshare 且能出网。
4. **趋势门槛的幅度（±1.0）与禁买阈值（30）都是拍定的**，尚无用实测数据校准的余地
   （回测接不进去）。`TREND_BUY_OFFSET` / `TREND_SELL_OFFSET` 是 `BaseStrategy` 类属性，
   `stop_buy_limit_down` 是 cfg 项。
5. **趋势门槛会让 swing 的选股集合变大**：原先被硬剔除的趋势向下股票现在会进候选
   （再由门槛决定买不买）。这是「改成门槛」的必然结果，不是缺陷，
   但会让选股列表变长、回测候选变多。
6. 盘后任务默认 15:10，由 `cfg/stock.cfg [scheduler] after_trading_hour/minute` 控制（`stock.cfg` 不入库，只提交 `.example`）。
7. 分钟缓存需在 15:10 时仍可用；若部署机内存吃紧导致当日分钟缓存被清，阀门会退化成 0（fail-open），日志有 INFO 可查。
8. **极端日的门槛可能高到不可达**（§2.1 末）。原先这等于「当天不开新仓」，
   是间接效果；三次修订后「跌停 >30 且破 S3」变成**显式禁买**（§2.3），
   但其它组合（如市场 +3.0 与个股 +2.0 叠加到 11.0）仍可能让门槛不可达。
