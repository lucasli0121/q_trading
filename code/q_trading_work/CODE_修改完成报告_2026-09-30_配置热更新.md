# 配置热更新：web 端改动自动跟随（2026-09-30）

## 一、问题与结论

在 web 界面改了用户策略参数、或改了股票池里的股票，运行中的 q_trading_work 不跟随，
要重启进程才生效。

原因是本端所有配置只在进程启动那一刻读一次：`_init_workflow` → `load_strategies_from_db`
加载完后，`strategy_params` 只留在实例上、`state.stock_pool` 只留在内存里，
之后没有任何刷新入口；池内容唯一的刷新点是每交易日 9:00 的盘前任务。

修法分两侧：服务端在写库成功后发布一条变更通知（主通道），本端收到后做一次增量对账；
本端另有一个 60 秒的定时对账（兜底通道，覆盖漏发通知、MQTT 掉线重连、进程早于服务端启动）。
对账结果是热更新已有实例，不重建实例。

## 二、本端对账覆盖的四类变更

`StrategyWorkflow.reconcile_user_strategies()` 拉三份服务端数据（策略模板、分配表、用户策略全量），
与本地运行表逐项 diff：

| 变更 | 处理 |
| --- | --- |
| 用户策略参数（用户参数 / 模板默认参数） | `instance.reload_params()` 重新解析并 apply，清该用户的打分缓存 |
| 股票池内容（同池增删股票） | `_reload_stock_pool()` 刷新 `state.stock_pool` |
| 股票池绑定（换池 / 解绑） | 重订阅新池 MQTT topic、退订无引用的旧池、刷新股票列表 |
| 用户策略增删、启停、持仓上限、初始资金 | 建实例 / 移出运行表 / 更新字段 |

四类变更里有三处不改就会静默失效，都在代码里单独处理了：

1. **换池要重订阅**。分钟行情按池订阅（`q_share/stock/minute/{pool_id}/#`），
   且 `handle_bar` 里有 `topic_pool_id != state.pool_id` 的过滤。只改 `state.pool_id`
   不重订阅，新池的行情一条都收不到。
2. **池内容变了要补跑当日选股**。策略的买入判定读「当日选股结果」
   （基类 `handle_minute_bar` 里 `code in select_stocks`）。盘中往池里加股票，
   不补跑选股的话那只股票要等第二天盘前才可能被选进来，表现是「加了票当天一直不买」。
3. **补跑不能清当日缓存**。`_run_daily_selection_for_state` 新增 `reset_cache` 参数，
   盘前任务传 `True`（调 `before_trading` 清缓存），盘中补跑传 `False`。
   分钟缓存与区间最高价是行情数据，与配置无关，清掉等于当天已跑的行情作废。

## 三、几个刻意的取舍

**分配表查询失败时不新增也不删除。** `_fetch_assigned_ids` 的返回值区分「查询失败」
与「确实没有分配」（`assign_ok`）。前者只对已有策略做字段热更新，不动策略集合；
后者才按分配表移除本地策略。反向的做法（查不到就当没分配）会让策略静默停止，
而界面上还显示运行中，同时多实例下这些策略又未必被别的实例接住。

**补跑选股有三道闸门**：只在交易时段（9:15 至 15:05）、只对 `requires_daily_selection`
为真的策略、同一策略 300 秒内只跑一次。补跑要对全池取日 K，是对账里最贵的一步，
用户连续点几次保存不能每次都跑。

`requires_daily_selection` 是本次新增的类属性，默认 `True`（基类 `handle_minute_bar`
就用选股结果），`SwingTradingStrategy` 显式置 `False`（它重写了 `handle_minute_bar`，
做 T 的信号覆盖全池）。实测生产 5 个策略的标记与预期一致。

**参数「有没有变」按解析后的生效参数判定，不按原始字典。** 三级回退是「择一」语义：
用户策略参数非空就整体忽略模板默认参数。界面上把用户参数清空，原始字典变了但生效值
只是落到模板默认值上；直接比较原始字典会误判成变更、每次对账都重载一遍。比较前
统一走 `_normalize_params` 解包 `{desc, value}` 包装格式。

**对账串行。** MQTT 通知与定时轮询可能同时到，而对账里的「建策略实例」「订阅 topic」
都不幂等（多订阅一次行情收两份）。非阻塞锁挡住并发，被跳过的那次 60 秒后还会再来。

**二次 apply 的基线问题。** 子类 `apply_params` 的回填写法是 `params.get(key, self.KEY)`，
第一次读类属性、赋值后 `self.KEY` 变成实例属性，第二次 apply 就回填成上一次的值，
参数只增不减（界面上删掉某个参数会静默失效）。修法是每次 apply 前先把上轮写进来的
属性还原（按上轮 diff 出的键，不按类属性全集，否则会误删构造参数），
`reload_params` 与构造期共用这一条路径。

## 四、验证

**单元测试**新增 `tests/test_config_reconcile.py`，31 项通过，覆盖池内容/绑定变更、
参数变更（含清空用户参数落到模板、原始值变但生效值不变两种边界）、策略增删、
分配查询失败的 fail-closed、补跑的四个闸门、二次 apply 的基线还原。

**全量回归**：570 passed, 2 skipped（8 分 55 秒，排除两个联网选股用例）。

**只读探针连生产服务端**（203.0.113.10:8000，不写任何数据）：

```
启动加载 5 个用户策略（3 个模板）
  6abb9a7e… 成交量策略盯盘   running pool=6
  6aab518a… 自选股波段策略   running pool=20
  6a662d50… 我的波段交易策略 running pool=22
  6a5ce385… 反弹交易策略     stopped pool=22
  6a58d62b… （用户策略名为空）running pool=9  max=0 amount=0

第 1 次对账：{"added": [], "removed": [], "updated": [], "assign_ok": true}
第 2 次对账：同上
RESULT: 首次对账无变更 = True | 两次对账结果一致 = True

requires_daily_selection: VolumeExpansion=True, SwingTrading=False, StrongRebound=True
```

「启动加载后立刻对账必须无变更」是这里最关键的一条：若加载路径与对账路径对同一个字段
的解读不一致，对账会每次报变更，60 秒一次触发补跑选股，把行情链路拖慢又不报错。

**服务端探针**（MQTT / Mongo 全用桩）：

```
topic: q_share/config_change
payload: {"scope": "user_strategy", "action": "update", "target": "us_123", "ts": ...}
publish 返回 False（未连接）→ notify_config_change 返回 False，不抛
publish 抛异常        → 返回 False，不抛
写接口挂载：user_strategy=3 处, stock_pool=4 处, strategy=2 处,
            blacklist=2 处, workflow_service_user_strategy=3 处
```

通知的调用点都在写库成功之后（`if not ok: raise HTTPException` 之后），
发布失败只记 warning，接口照常返回成功。

## 五、部署

服务端 q_trading_server 需重新部署（本机容器代码已挂载，但需要重启进程；
生产实例在 203.0.113.10:8000）。本端 q_trading_work 重启一次后生效。

部署后的两个验证动作：

1. 在界面改一条运行中策略的参数，本端日志应出现
   `收到配置变更通知: topic=q_share/config_change` 与 `配置对账完成 … 更新 1`；
2. 往运行中策略的股票池加一只股票，日志应出现
   `股票池内容变化: 新增 ['xxxxxx']` 与 `配置变更后补跑当日选股`。

即使通知通道不通（例如两边 MQTT broker 不同），60 秒的定时对账也会把改动带上，
只是延迟更长，非交易时段放宽到 5 分钟。

## 六、已知限制

- `_reload_stock_pool` 每次对账都会对每个策略发两次 HTTP（池信息 + 池内股票）。
  5 个策略、交易时段 60 秒一轮，约每分钟 10 个请求。
- 模板缓存只增不删：模板被删后旧条目留在 `_strategy_templates` 里。这不影响运行中的策略，
  只影响「绑定已删模板的新用户策略」会被尝试实例化，实例化时会因取不到类而失败并记 warning。
- 对账不发重试：分配表查询失败后不做重试，等下一轮（最长 60 秒）。
  启动路径保留原有 3 次重试，覆盖后台尚未就绪的启动瞬间。
- 通知的端到端链路（服务端 publish 到本端收到）无法在本机验证：本机服务端连的是
  192.168.1.63 的 broker，本端配置连的是 example.com。需在真实部署上按第五节验证。
