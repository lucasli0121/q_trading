## 二、R1（阻断）：两个策略无法实例化

`workflow/strategy_workflow.py:355-370` 现在把 `user_strategy_name` 透传给策略类：

```python
instance = strategy_cls(
    user_strategy_id=user_strategy_id,
    user_strategy_name = user_strategy_name,   # 新增
    ...
)
```

但 `SwingTradingStrategy.__init__`（72-88）与 `StrongReboundStrategy.__init__`（73-89）的签名里**没有这个参数**，只有 `BaseStrategy.__init__` 有。实测：

```
TypeError: StrongReboundStrategy.__init__() got an unexpected keyword argument 'user_strategy_name'
```

`_instantiate_strategy` 内部 `except Exception` 会把它兜住并记 ERROR 后返回 `None`，后果是该用户策略被整个跳过：**不建仓、不发信号、不卖**。

实测影响：`tests/test_strategy_workflow.py` 9 条失败，全部指向这一条。

修法（两处 `__init__` 各加一行，并把值继续传给 super）：

```python
def __init__(self, user_strategy_id="", user_strategy_name="", strategy_id="", ...):
    super().__init__(user_strategy_id=..., user_strategy_name=user_strategy_name, ...)
```

注意第二半是必需的：即使补了签名，若不往下传，`self.user_strategy_name` 仍是 `""`，两个策略里新换的那批日志前缀（`f"{self.user_strategy_name},func:_check_buy_conditions,..."`）会变成以逗号开头的空名字。

**答复**: 修改，同时在workflow中发送trade notify时 也需要更改为user_strategy_name，不再用strategy_name

## 三、R2（高）：量价配合的符号写反

`strong_rebound_strategy.py:400-403`：

```python
if row['vol_price_align'] == 1:
    score += 2.0
elif row['vol_price_align'] == -1:
    score -= -2.0      # ← 等价于 +2.0
```

`vol_price_align == -1` 的含义是「价跌量增」（恐慌出逃，应为减分）。同源的 `VolumeExpansionFactor.score:182-183` 写的是 `score -= 2.0`，是对的。

实测（12 根分钟线，价格每根下跌、成交量每根放大）：

```
strong_rebound._check_volume_price_condition -> ok=True signal=BUY score=1.0
VolumeExpansionFactor.score（同一份构造）    -> score=-3.5 signal=None
```

即同一份「越跌越放量」的数据，强趋势策略判成 BUY 并把 `+1.0` 计进买入分。修法是 `score -= 2.0`。
**答复**: 修改

## 四、R3（高）：支撑位表为空时判定崩溃

`swing_trading_strategy.py:339-340`：

```python
sr_df: pd.DataFrame = self._get_sr_points(code)
inday_score: float = inday_sr_factor.score_with_sr(sr_df, stock_df)
```

`_get_sr_points`（254-267）在日线取不到时会返回**空 DataFrame**，这是它自己的设计（223-229 的注释也写了「由下游按无点位处理」）。但下游 `InDaySRFactor.score_with_sr` 没有空表保护：

```python
rs_records = sr_df.to_dict(orient="records")
recent_rs_record = rs_records[-1]     # 空列表 → IndexError
```

实测：

```
1) InDaySRFactor.score_with_sr 传入空 sr_df -> IndexError: list index out of range
```

`_check_buy_conditions` 的 `except Exception` 会兜住并记一条 warning，函数返回 False。净效果是：**该股票在这条策略下永远不会产生买卖信号，且每分钟刷一条 warning**。触发条件不罕见：新股上市首日、停牌复牌、日线取数失败（服务端只留 3 个月，回源可能超时）都会走到这里。

同一函数里 `stock_array`（分钟缓存）为空时 `recent_stock = stock_array.to_dict(...)[-1]` 会抛同样的错，只是正常链路下 workflow 先写缓存再派发（`strategy_workflow.py:1138`），概率低。

**回复**: 修改

## 五、R4（高）：波段策略绕过了「当日选股」闸门

基类 `handle_minute_bar`（`base_strategy.py:328-341`）的买入闸门是「在当日选股列表中 **且** 无持仓」，子类 `SwingTradingStrategy.handle_minute_bar`（164-178）把它整个覆盖掉了，只判断 `_break_max_r`：

```python
break_max = self._break_max_r.get(code, False)
if not break_max:
    match, extra = self._check_buy_conditions(code, stock_data)
```

而 `_break_max_r` 只在 `is_match_strategy` 里被赋值，且仅在 `KlineSRFactor.score == -10.0` 时为 True。也就是说**选股结果本身不再参与盘中买入判定**，只通过「昨日是否突破最大阻力位」间接生效一次。

实盘与回测的股票集合因此不同：

- 回测（`backtest_engine.py:872-879`）：`codes_today = matched_codes + held_codes`，只对当日选中的候选股和有持仓的股票跑 `handle_minute_bar`；
- 实盘（`strategy_workflow.py:1134-1154`）：派发条件是「topic 里的 code 在 `state.stock_pool` 内」，即**整个股票池**。

结果：回测里根本不会被评估的池内股票，实盘每分钟都在跑买入判定并可能产出 BUY 信号（信号会写库、会推 MQTT，随后才在下单环节被持仓上限等条件拦住）。

若这是有意为之（把池当交易域、用盘中支撑位触发），建议在类 docstring 里写清楚「不依赖当日选股结果」，并把 `before_trading` 里为全池预计算支撑位的做法与之一致；若不是，则应在 `handle_minute_bar` 里补回 `self._load_select_stocks(...)` 判定。

顺带一个同源的差异：实时链路恒传空持仓（D-1/X1 决策），所以卖出判定会对**池内所有未持仓股票**执行，这类「未持仓的卖出信号」会被写库并推送（`_save_trade_signal` 在持仓检查之前，`strategy_workflow.py:1271`），而回测只会评估候选股与持仓股。两条链路的信号集合不可直接比较。
**答复**: 这个设计是对的，strategy_workflow策略目的是检测波段做T操作，增加波段操作的信号覆盖面

## 六、R5 / R6 / R7：三个因子层面的问题

这三处的根因在 `factor/` 目录下的其它文件，但都由被检视文件直接调用，一并列出。

**R5：`KlineSRFactor.score` 的 ±7.5 是死代码**（`kline_support_resistance.py:76-92`）

支撑档按升序聚类，`s[0]` 最小、`s[-1]` 最大。代码顺序是 `price <= s[0] → 10`、`price <= s[-1] → 5`、`price <= s[1] → 7.5`。第三支要求 `price > s[-1]` 且 `price <= s[1]`，而 `s[1] <= s[-1]`，恒不成立；阻力侧同理。实测（构造 4 档支撑 + 4 档阻力，共扫 7 个价位）：

```
支撑档数=4  [8.65, 9.25, 9.85, 10.45]
阻力档数=4  [11.0, 11.6, 12.2, 12.8]
price= 7.650 -> 10.0     price= 8.650 -> 10.0
price= 8.950 ->  5.0     price= 9.550 ->  5.0
price=14.800 -> -10.0    price=12.800 -> -10.0   price=11.300 -> -5.0
```

实际只会出现 10 / 5 / −5 / −10。另外 `price <= s[-1]` 拿到 5 分意味着「价格低于最高的那条支撑」也算买点，语义上偏松，建议一并确认档位定义。
**答复**: KlineSRFactor支撑和阻力因子中，打分逻辑是：当股价<=最小支撑位时 10分，当股价位于最小和最大支撑位时 7.5分，当股价只小于最大支撑位时 5.0分。 但是支撑位个数有时会大于等于3个，有时只会出现2个，甚至只会出现1个。阻力位也一样。
这样就需要判断长度，如果支撑位只有2个，那么股价小于等于s[0] 10分，当股价小于等于s[1] 5分，（不会出现7.5分情况）。
只有支撑位个数大于等于3时才会出现7.5分情况

**R6：`BollSRFactor` 在 window=5 下只有 ±5 与 0**

`r1 = 中轨+2σ`、`r2 = +4σ`、`r3 = +6σ`（`boll_support_resistance.py:54-74`），而布林带窗口**含当根价格**，单点对均值的最大偏离是 `√(n−1)·σ`，n=5 时等于 2σ ⇒ r2/r3/s2/s3 恒不可达。实测：

```
price=10.0（整段同价）-> -10.0     price= 9.0 -> 5.0
price= 8.0 ->  0.0                 price= 7.0 -> 5.0
price=11.0 ->  0.0                 price=12.0 -> -5.0   price=13.0 -> -5.0
```

两处值得注意：

1. 档位表写着 ±10/±7.5/±5，实际参与打分的只有 ±5 与 0，`avg_score` 的取值空间比预期窄一半；
2. **零波动窗口（std=0）时三轨与中轨重合，`price >= r3` 成立，score 恒 −10**。一字板、极不活跃股票都会命中。在波段策略的卖出侧这会把 `avg_score` 直接压成负值并触发 SELL；在买入侧则会挡掉买点。
**答复**: 给出合理意见，可以修改

**R7：`MultiTrendFactor` 改尺度后阈值没跟着改**

在途改动把 `return score / total_score * 10` 改成了 `return score`（`multi_trend_factor.py:101-120`），满分由 10 变成 7（3+3+3+0.5+0.5）。而 `UP_TREND_SCORE = 6.0`、`cfg/strategy.yaml` 的 `up_trend_score: 6.0` 是按旧尺度定的：旧尺度下 6.0 只要求满分的一半多一点，新尺度下要拿到 6.0 必须「MA5>MA10（3 分）+ ADX 确认（3 分）」两项全中，`vwap`/`prev_high` 的 1 分补不上缺口。实测各分项的有效性：

```
n= 10  根 -> score=4.0   NaN: adx / macd_dif / macd_hist
n= 20  根 -> score=7.0   NaN: macd_dif / macd_hist
n= 34  根 -> score=7.0   无 NaN
```

MACD 需要 26+9−1=34 根才有值，ADX 需要约 2×period 根。实盘选股只取 20 根日线（`strategy_workflow.py:2300` 的 `days=20`，回测 `signal_window=20` 一致），所以 **`macd_hist` 这一项在两个链路里永远是 NaN，那 3 分从来没拿到过**。要修的是尺度和窗口二选一：要么把 `total_score` 归一化加回去，要么把阈值按 7 分制重标，并把日线窗口放到 40 根以上让 MACD 真正参与。
**答复**: 这个问题是在strong_rebound_strategy出现的吗？

## 七、R8 / R9 / R10 / R11

**R8：买入分硬除以 2。** `strong_rebound:294-297`：

```python
score += trend_score
avg_score: float = score / 2
res: bool = avg_score >= self.BUY_MIN_SCORE
```

固定除以 2 隐含「两个分量各自满分」的前提，但成交量条件不成立时（`ok=False` 或 `signal != "BUY"`）只有趋势分进入分子，仍被除以 2，等于把趋势阈值抬高一倍。按当前配置算上限：成交量侧最高 5.5（2.0+1.5+2.0），趋势侧最高 7.0，`avg` 上限 6.25，而 `cfg/strategy.yaml` 的 `min_score: 6.0`、`trend_minutes_limit: 10`（ADX 要 20 根、MACD 要 34 根才有效）。结论：**10:04 之前（分钟内 34 根）在数学上不可能触发买入，之后也必须两侧几乎同时打满**。这类阈值建议按「实际可达上限」反推，或改成按分量加权平均。

**R9：SELL 信号的 reason 丢失。** `strong_rebound:534` 写的是 `extra["reasons"]`，而 `_save_trade_signal`（`strategy_workflow.py:1528`）读的是 `extra.get("reason", "")`。实测影响：卖出信号的 `reason` 字段与 MQTT 载荷里该字段为空，日志里也看不到卖出原因（其余 `reason`/`reasons` 混用只此一处）。

**答复**: strong_rebound中的_check_buy_conditions检测条件是趋势和成交量，成交量为主，趋势为辅，成交量的打分权重更高，依次逻辑修改这部分代码

**R10：持仓最高价查询的调用频率与文档。** `_resolve_highest_price` → `_get_highest_since_buy` 每次卖出判定都发一次 `GET /api/market/kline/day`，而且**没有任何缓存**：实时链路里卖出分支对池内每只股票每分钟都会走到（见 R4 的说明），300 只池就是一分钟 300 次请求，而结果在日内几乎不变。另外 570-572 行 docstring 写「end 用于推算区间结束日（其上一交易日，即不包含当日未完成的K线）」，实现里 `end_day = today_str` 直接用了 `create_time`，并未做上一交易日换算，实际区间**包含当日**（服务端 `start`/`end` 是字符串比较，含时间也能匹配当日）。建议加日内缓存（key 用 code+日期），并把文档改成实际口径。

**答复**: `end_day = today_str`的原因是 _get_highest_since_buy只获取最近做高点价格，至于是今天的还是昨天的不重要，只需要最近两天的最高点
反复读取日K线是应该缓存，还是做二级缓存在user_strategy_cache中实现。

**R11：`VwapFactor.days` 无效。** `vwap_factor.py:21-33` 的 `calculate` 通篇没用 `self.days`，对整张表求和，所以构造时传的 `SELL_VWAP_LIMIT`（配置里 `vwap_minutes_limit: 10`）不起任何作用，算出来是**当日累计 VWAP**。另外 `calculate` 先 `round(result, 2)` 再在 `score` 里算百分比，对低价股会引入固定的相对误差。
**答复**: 可以修改

## 八、低优先与契约问题

**R12** `volume_expansion_factor.py` 两处口径问题：

- `score()` 的 docstring 列了「量比 25 分、连续放量 20 分、趋势 15 分、量价 20 分、OBV 10 分、价格位置 10 分」（100 分制），实现的实际量程是 11.5 分（2 + 2.5 + 1.5 + 2 + 1.5 + 2），`signal` 阈值 4.0/6.0 是按 11.5 分制定的，两者对不上；
**答复**: 统一按照10分制，修改docstring
- `score()` 返回 **dict**，而 `BaseFactor` 家族其它因子（`KlineSRFactor`、`BollSRFactor`、`MultiTrendFactor`、`VwapFactor`、`LowReboundFactor`）都返回 float。目前没有调用方，所以没炸；一旦有人按因子惯例写 `score += factor.score(df)` 就会 `TypeError`。另外 137-138 行 `else: score = 0.0` 是整体清零而不是局部变量，现在恰好因为「条件1 是第一个计分项」所以无害，重排顺序就会踩坑；同源的 `strong_rebound:382-383` 用的是局部变量，写法更安全。
**答复**: 返回**dict**的问题，可以加个说明或者强制指定返回值，score = 0.0表示当没有上涨时不计分
**R13** 涨跌幅判定的两个边角：

- `preclose == 0`（数据不全）时 `(current_price - preclose) / preclose * 100` 会除零，被外层 `except Exception` 兜住 → 变成「检查异常」日志并刷 warning。`strong_rebound` 买入分支在 238 行挡住了 `preclose <= 0`，`swing` 的两处没有；
- 阈值硬编码 `±9.0%`（按 10% 涨跌停留 1% 余量）。池里已有 300xxx/301xxx/688xxx（20% 涨跌停）与 ST（5%）：创业板股票涨到 +9.5% 会被判成「接近涨停，不卖出」，ST 涨到 +5% 封板却仍会去挂卖单。
**答复**： 可以修改

**R14** `strong_rebound` 23-26 行三个导入（`HighDeclineFactor`、`KlineSRFactor`、`VolumeExpansionFactor`）在本次重构后已无引用（原 `init_factors` 注册因子的代码被删成 `pass`）；`swing:287` 的 `low_price`、两个策略算出的 `star` 都没有下游使用（`_save_trade_signal` 只取 signal/current_price/reason）。


**R15** `dao/trade_signal_dao.py` 新增了 `score`/`star`，`TradeSignalApi.add()` 与 `_save_trade_signal` 的调用参数都没带上，两个字段恒为默认 0，服务端收到的一直是空值。要落地这条，需要 `add()` 加参数并透传。
