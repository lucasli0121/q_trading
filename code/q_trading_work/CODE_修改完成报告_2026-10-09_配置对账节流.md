# 配置对账节流修复报告

日期：2026-10-09
改动文件：`workflow/strategy_workflow.py`、`tests/test_config_reconcile.py`
状态：已改完，待重新打包部署

## 一、问题

生成机器的 apscheduler 日志显示，`配置对账（热更新）` job 每分钟都报
`executed successfully`，但单轮耗时**严格交替**：

| 轮次 | 耗时 | |
|---|---|---|
| 09:51 | 365ms | 真跑了 |
| 09:52 | 1ms | 被拦 |
| 09:53 | 335ms | 真跑了 |
| 09:54 | 0ms | 被拦 |
| 09:55 | 415ms | 真跑了 |
| 09:56 | 0ms | 被拦 |
| 09:57 | 385ms | 真跑了 |
| 09:58 | 0ms | 被拦 |

实际对账周期是 **120 秒**，不是设计的 60 秒；非交易时段 600 秒，不是 300 秒。

**不是定时器故障。** apscheduler 每 60 秒准时触发，`Running job` 与
`executed successfully` 每轮成对出现、时间戳严格间隔 60 秒。被拦掉的是业务代码
自己的节流判断。

## 二、根因

三处代码互相咬住：

| 位置 | 代码 | 作用 |
|---|---|---|
| `strategy_workflow.py` 149 行 | `RECONCILE_INTERVAL_SECONDS = 60` | 节流阈值 |
| 2994 行 | `IntervalTrigger(seconds=RECONCILE_INTERVAL_SECONDS)` | 定时器每 60 秒调一次 `_reconcile_job` |
| 1574 行（旧） | `if time.time() - self._last_reconcile_ts < interval: return` | 距上次不足阈值就返回 |
| 1102 行 | `finally: self._last_reconcile_ts = time.time()` | 时间戳记在**对账结束**时刻 |

阈值（60）恰好等于触发周期（60），而时间戳记的是结束时刻，单轮对账要跑
0.35~0.42 秒：

```
第 N 轮   09:51:38.560 开始 → 09:51:38.925 结束，ts = 38.925
第 N+1 轮 09:52:38.560 开始 → 距上次 59.635 秒 < 60 → 直接 return
第 N+2 轮 09:53:38.560 开始 → 距上次 119.635 秒 ≥ 60 → 正常执行
```

永远差那 0.3 秒，于是稳定「一轮跑一轮跳」。跳过的轮次直接 return、
一行日志都不打，apscheduler 照样报 `executed successfully` —— 光看调度器日志
看不出被跳过，只能从耗时 0ms 反推。

## 三、修法

**给节流阈值留余量**，新增类属性：

```python
RECONCILE_THROTTLE_RATIO: float = 0.9
```

`_reconcile_job` 改为与 `interval * RECONCILE_THROTTLE_RATIO` 比较
（交易时段 54 秒、非交易时段 270 秒）。只要单轮耗时不超过周期的 10%（6 秒）
就能每轮都跑，恢复设计的 60/300 秒。

**跳过时打一行 INFO**（不是 DEBUG）。根 logger 是 INFO，DEBUG 记录压根不产生
（console handler 虽是 DEBUG，但被 root 的级别拦在前面），被跳过就只剩
apscheduler 那条耗时 0ms 的 `executed` 可反推。修好后跳过是罕见事件，
这行不会污染日志。

不用「把时间戳改记在开始时刻」的方案：边界恰好等于 interval，浮点上仍会翻车。

## 四、验证

**只读探针**（模拟 apscheduler 绝对时刻触发 + 单轮 0.37 秒耗时，不连服务端）：

```
旧行为 ratio=1.0: 8 轮触发里真执行 4 轮
  执行轮次: 0.00s, 120.00s, 240.00s, 360.00s
  实际周期: 120 秒（每两轮跳一轮）

本次修复 ratio=0.9: 8 轮触发里真执行 8 轮
  执行轮次: 0.00s, 60.00s, 120.00s, 180.00s, 240.00s, 300.00s, 360.00s, 420.00s
  实际周期: 60 秒
```

旧行为下探针还打出了被跳过的原因：`配置对账跳过（距上次结束 59.6s，不足节流阈值 60.0s）`，
与线上日志的交替耗时完全对应。

**新增 3 项测试**（`tests/test_config_reconcile.py`）：

- `test_scheduler_not_skipped_when_one_round_takes_a_while` —— 模拟「上一轮
  59.6 秒前才结束」，要求仍然执行。这是本 bug 的守卫，取满阈值时必失败。
- `test_throttle_ratio_leaves_margin` —— 余量必须 < 1，且要显著大于单轮耗时。
- `test_throttled_round_is_logged` —— 被跳过时必须有 INFO 留痕。

**突变验证**：把 `RECONCILE_THROTTLE_RATIO` 改回 `1.0` 重跑，
上述前两项失败（2 failed, 3 passed），确认测试真的能抓住旧行为。

**回归**：`tests/test_config_reconcile.py` 35 passed；全量
**597 passed, 2 skipped**（8 分 36 秒）。

## 五、部署

代码改动在源码里，生成机器跑的是 `dist/q_trading_work-latest` 打包产物，
**需要重新打包再部署**。部署后可在生成机器上按这个办法确认：

正常情况 `Running job` 与 `executed successfully` 的耗时应当**每轮都是几百毫秒**，
不再出现交替的 0ms/1ms。若某轮出现 `配置对账跳过（距上次结束 …）`，
说明该轮对账耗时超过周期的 10%（6 秒），需要看那轮为什么慢。
