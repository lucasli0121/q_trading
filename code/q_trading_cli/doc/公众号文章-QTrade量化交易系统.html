它是什么

QTrade 分三层：策略引擎（q_trading_work）定时取数算信号下单，数据接口层（q_trading_server）用 FastAPI + MongoDB + Redis 对外供数，你正在用的这个 q_trading_cli 是 Web 客户端。

它的边界很明确：不碰数据库、不跑策略，只做展示与干预。好处是客户端可以独立部署、独立发版、独立回滚——改界面文案不用动交易引擎，引擎半夜崩了也不影响你查历史数据。反过来，客户端出 bug 顶多看到数字不对，不会误下单。

什么时候会打开它

1盘前 · 今天买什么
策略选股页按实例分 Tab，看当天选出的股票、现价、涨跌幅。红涨绿跌，和所有 A 股软件一致。顺手看股票池同步是否正常。
2盘中 · 信号与启停
监控页顶部四张信号统计卡，中间策略卡片显示已运行多久、持仓数、浮动盈亏，底部实时信号表：时间 / 策略 / 代码（带名称）/ 类型 / 成交价 / 盈亏率 / 原因。信号由 MQTT 推来，看到 undesired 信号直接在卡片上启停。
3盘后 · 这周怎么样
仪表盘的累计收益曲线，右上角下拉选一个策略叠加琥珀色对比线，日期取并集，缺数据断线不补 0。回测记录页看指标与逐笔成交。
4离开屏幕之后
个人喜好页开企业微信 / 短信推送，各配一个推送星级滑块（0 ~ 5.0 星，步长 0.5，0 表示不限）。低质信号刷屏是监控系统最常见的死法。

它给谁用

主要用户是自建策略的量化交易者：懂 Python 和 K 线，用现成模板（强势反弹、趋势追踪、网格交易、多因子选股）跑实盘，只是不想每次查数据都开终端 curl 接口。他们要的是"策略跑得怎么样、我该管还是该放"。

次要用户是跟着信号做决策的人，不改参数，只关心今天出了什么信号、选了哪几只票。

不适合的场景也要说清楚：需要自己写因子代码、需要 tick 级数据、需要 24×7 无人值守盯盘——那是策略引擎和小程序端的活。移动端由微信小程序承担，接同一套后端 API。

四个做得细的地方

  • 创建策略是一个表单，不是向导。选模板卡片 → 配股票池 → 填参数 → 勾"立即运行"（默认勾上，创建即 running），不用创建完再去列表页改一遍状态。
  • 回测记录页的返回按钮跟随入口。从监控进就回监控，从列表进就回列表，侧边栏高亮也跟着变。
  • 持仓盈亏是现算的。接口返回的盈亏率是成交时点快照，买入写入、卖出才重算，直接显示就是过期数字。页面一律用「成本价 + 数量 + 实时价」现推，缺价显示 --。
  • 状态选项不会静默改掉你的设置。后端 error 是故障态不可选，但若某策略当前恰是 error，编辑框会临时补进下拉——否则会出现"下拉空白、保存时写回旧值"。

体验上的几个决定

  • 颜色全部走设计令牌。一份 TOKENS 字典，一个变量名对应深浅两套值，切主题会话级即时生效、零重渲染。图表配色单独一套 API，因为 ECharts 画在 canvas 上读不到 CSS 变量。
  • 数字错误会说人话。4xx 会提取后端 detail 显示，而不是甩一串 Client error '409 Conflict' for url ...。401 弹确认框跳登录。
  • 刷新不会打爆后端。行情 30 秒 TTL、策略表 60 秒会话节流，信号靠推送；收益曲线只在构建、切换周期、切换对比策略时重算，不做无意义定时刷新。
  • 深色模式即时保存，不是"改了要记得点保存"。

它是怎么被验证的

这类界面最怕"看着对、数字错"。所以验证分三层：

  • 桩冒烟——把 nicegui、app_context 等依赖替成桩，真跑一次页面入口函数，断言不抛异常、DOM 结构符合预期。六个页面各一份（概要 115 项、监控 82 项、回测 91 项、列表对话框 64 项、喜好页 30 项）。
  • 反向验证——把源码指向一份"故意改坏"的副本再跑，要求它必须报错。"当天多条记录相加"这种真实发生过的口径错误被写成专门用例守着，目前 101 个改坏用例全部被抓到。它验证的不是"现在对"，而是"以后改坏了会被立刻发现"。
  • 真机对账——涉及"数字对不对"的结论必须起真实实例、连真实后端、读渲染后的图表数据，与独立复算逐点比对。桩检查只能证明不抛异常。

最后

量化交易真正的瓶颈通常不在算信号，而在看懂并干预：收益是多少、哪些策略该停、今天出了什么信号、浮盈是正是负。

QTrade 把这四件事收进一个登录后即用的界面，并且刻意不碰交易本身。前端可以随便改，引擎必须稳。这条边界是系统能长期跑下去的前提。
